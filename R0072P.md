## Stacked-Bar Movement (Diagnostic B)

### Test setup

The Search deck was chosen as a non-overflowing deck (3 compact bars, no active-card content expansion). Note: all three Search deck cards are `disabled: true` in the source.

### B1 — Mid-drag physical movement (disabled cards)

| Measurement | Value |
|---|---|
| Bar Y before drag | 616.0 px |
| Bar Y during 80 px upward drag | 616.0 px |
| Y shift | **0.0 px** |
| Transform before drag | `matrix(1, 0, 0, 1, 0, 0)` (identity) |
| Transform during drag | `matrix(1, 0, 0, 1, 0, 0)` (unchanged) |

**Result for disabled cards: no physical movement — PASS for this condition.**

### Limitation — lift mode on enabled cards not confirmed

The source code in `DeckInactiveCard` contains:

```
d.mode = canDeckScroll() ? 'scroll'
  : (totalDy < 0 && !card.disabled ? 'lift' : 'scroll');
```

On a **non-overflowing deck with an enabled (non-disabled) card**, an upward drag of ≥ `DRAG_ACTIVATE` (48 px) sets the card's CSS `translateY` and activates it on release. This path was **not exercised** in DiagB1 because the Search deck's cards are disabled and skip the lift branch. Lift behaviour for enabled cards on non-overflowing decks is confirmed in source but not runtime-proven by this diagnostic.

### B2 — Drag does not activate disabled cards

- Dragged 100 px upward (well past 48 px threshold) and released on Search deck.
- All 3 stacked bars remained visible after release (count = 3).
- **PASS** for disabled cards. Enabled-card drag-to-activate was not tested (see B1 limitation).

### B3 — Normal tap activates an enabled stacked bar

- Tapped "List Actions" bar in the More deck.
- `deck-panel` became visible immediately after tap.
- **PASS** — taps work normally.

**Overall Diagnostic B verdict: INCONCLUSIVE for the lift path.** Runtime confirmed: disabled cards never lift. Source confirms: enabled non-disabled cards on non-overflowing decks DO enter lift mode and CAN activate via drag. This is an unverified defect risk.

Unselected items appear visually dimmed, not absent.

The spec requires: "The preview contains ONLY currently SELECTED items."

## Diagnostic Questions

**Q1. What is the measured category-bar height?**
**68 px** (first `[data-swipe-key]` bounding box).

**Q2. What is the measured stacked-bar height?**
**56 px** (first inactive card in Search deck bounding box).

**Q3. Are they actually the same size?**
**No.** Difference is 12 px. The source constant `BAR_PEEK_H = 54` sets `minHeight` on stacked bars; with borders the rendered height is 56 px. Category bars render at 68 px. **FAIL.**

**Q4. Does a stacked bar physically move/lift during an upward drag?**
**Not confirmed at runtime.** DiagB1 tested on disabled Search deck cards only — these skip the lift path entirely. Source code confirms that an enabled card on a non-overflowing deck DOES enter lift mode (`translateY(-lift)`) up to 120 px. This was not exercised at runtime in this diagnostic.

**Q5. Can a stacked bar activate because of a drag/release rather than a tap?**
**Not runtime-confirmed for enabled cards.** Source code line 1034: `if (mode === 'lift' && lifted >= DRAG_ACTIVATE) { setLift(0); onActivate(); return; }` — drag of ≥ 48 px upward on an enabled non-overflowing deck bar activates it. Disabled cards cannot activate. DiagB2 used disabled cards and gave a vacuous pass.

**Q6. Does a normal tap still activate it?**
**Yes.** DiagB3 confirmed a tap on the "List Actions" bar in the More deck activates the card. **PASS.**

**Q7. What selected item was used for the Preview test?**
`Osprey Atmos 65` (`checked: true`, Backpack category, DEMO_SEED item `b1`).

**Q8. What unselected item was used?**

**Q23. What is the smallest safe correction for every CONFIRMED failure?**

*CONFIRMED FAILURE 1 — Stacked bar height ≠ category bar height (12 px gap):*
Change `BAR_PEEK_H` from `54` to `68` in `MobileFunctionalV3.tsx`. The constant drives `minHeight` on the inactive card div (line 1093) and the active card's `minHeight` (line 1255). Verify the deck layout still fits the viewport after the change.

*CONFIRMED FAILURE 2 — Preview shows all items (not selected-only):*
In the `PreviewOverlay` component (function added by R0072 around line 278), change `filterToChecked={false}` to `filterToChecked={true}` and remove `checklistUse={{}}` / `onToggle={() => {}}`. With `filterToChecked={true}` and no `checklistUse`, PreviewBody enters "legacy mode" (line 92: `isChecklistUseMode = false`) and filters to `item.checked === true` items (line 142–143), displaying each with a static filled/empty checkbox — correct for a read-only print preview.

*UNCONFIRMED RISK — Stacked bar lift/drag-activate on enabled non-overflowing decks:*
If confirmed as a defect, the smallest fix is to remove the `'lift'` branch entirely from `DeckInactiveCard.onPointerMove`, keeping only `'scroll'` mode. This makes stacked bars tap-only with no lift gesture. A targeted test would need a non-overflowing enabled-card deck (e.g. a custom short More-like deck with 2–3 enabled cards).

**Q24. Which exact application file(s) would need to change?**
`artifacts/pack-checklist/src/pages/MobileFunctionalV3.tsx` only — for all three corrections above.

**Q25. Which currently passing R0072 behaviours are at risk from those corrections?**

- *BAR_PEEK_H change:* All 60 R0072 tests should continue to pass; no test checks the exact pixel height of stacked bars. Deck layout visual regression risk only.
- *filterToChecked change:* The existing R0072 test "Preview opens a checklist-style preview overlay" only checks that `window.print` is not called and that the overlay title is visible — it does not check item content. Changing to `filterToChecked={true}` would break the old R0072 test `DiagC2` check IF the seeded list has no checked items; but DEMO_SEED has 16 checked items so this is safe. The test checking unselected item exclusion (C3) would flip from FAIL to PASS.
- *Lift mode removal:* No R0072 test exercises stacked-bar drag-to-activate. Removing lift mode would cause no test regressions.
