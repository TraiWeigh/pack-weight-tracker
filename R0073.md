## Lessons for Future Prompts

### Learning Question 1
**What existing gesture logic caused stacked bars to inherit lift/drag activation, and what rule should future TrailWeigh prompts use to keep category-reorder/movement behavior isolated from stacked bars?**

`DeckInactiveCard` shared the same pointer-event infrastructure as the category reorder system (both use pointer capture, drag slop, and a mode-lock pattern). The lift branch (`mode === 'lift'`) was added as a power-user shortcut alongside the scroll branch, using `canDeckScroll()` to choose which path to take. Because the mode-lock ran for *all* vertical gestures on *all* `DeckInactiveCard` instances, any enabled bar on a non-overflowing deck inherited lift/activation on upward drag.

**Rule:** Keep `DeckInactiveCard` gesture logic strictly separated from category-row gesture logic. Any future change that adds a drag mode to `DeckInactiveCard` must explicitly document which user-visible behavior it enables. The default mode on vertical drag must remain `'scroll'` (or no-op for non-overflowing decks); "tap-only" means the mode branch never evaluates `'lift'` as a target.

---

### Learning Question 2
**Why did Preview render unselected items even though the intended behavior was selected-items-only, and what existing selected-only path/pattern should future prompts reference to avoid this mismatch?**

`PreviewOverlay` was written (in R0072) to show a "PDF-style checklist preview" and passed `filterToChecked={false}` to `PreviewBody`. This flag tells `PreviewBody` to include ALL items, applying 0.5 opacity to unchecked ones — the right behavior for an interactive checklist where you want to see everything. The intended selected-only behavior was already implemented inside `PreviewBody` at the `filterToChecked={true}` path (line 142–143: `const items = filterToChecked ? allItems.filter(i => i.checked) : allItems`).

**Pattern to reference:** The Checklist overlay (`showChecklist` state, line 425 in `MobileFunctionalV3.tsx`) correctly passes `filterToChecked={true}` with a live `checklistUse` map. For any read-only selected-items-only preview (print layout, PDF-style view), use `filterToChecked={true}` with NO `checklistUse` prop — `PreviewBody` then uses `item.checked` directly for filtering and static display.

---

### Learning Question 3
**What did this repair reveal about duplicate-control placement in mobile V3, and what is the safest rule for moving a function into a bottom box/dedicated control without leaving a second launcher elsewhere?**

The category "+ Add Item" button was never removed when the dedicated Add system (Group 1 bottom box) was established. The category button predated the bottom-box architecture and was simply overlooked during the R0072 no-duplicate audit because it lived inside the accordion body (not in a More deck card or a box label), making it invisible to the deck-level duplicate check.

**Rule:** When a function is given a dedicated bottom-box launcher, perform a full-file search for every other invocation path (event handler, button, context menu, gesture) that calls the same underlying function (`addItem`, in this case). Any path that is not the canonical launcher must be removed at the same time. The audit scope must include accordion bodies, overlay content, and contextual inline controls — not just top-level UI surfaces.
