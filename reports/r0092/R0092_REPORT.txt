ROOT CAUSE OF PRIOR BOTTOM-BAR MOVEMENT
The bar was fixed only to `bottom: 0` in the layout viewport. Safari can expose a
shorter/offset visual viewport while its browser chrome changes; without compensating
for that measured bottom gap, a layout-fixed layer can appear to travel relative to the
usable viewport even though no React scroll handler moves it.

SMALLEST COHERENT FIX
- Measure `window.innerHeight - (visualViewport.offsetTop + visualViewport.height)`
  on window and visualViewport resize/scroll events.
- Use that measured gap as the fixed Bottom Box Groups bottom offset. It is 0 in normal
  Chromium/desktop conditions and becomes active only when Safari exposes a shorter or
  offset usable viewport.
- Add the same offset to the root content bottom reservation and every raised deck's
  bottom offset, so final content, decks, and the fixed bar remain synchronized.
- Retain native document scroll; no body lock, overflow:hidden main-page lock, viewport
  metadata change, or app-height redesign was introduced.
- Use the preserved category-weight unit edge (x=358px at 402px) as the shared right-side
  master line: Summary category/Selected text and the terminal AppBar box icon now end
  on that line. The whole non-hamburger AppBar content remains one structural group
  bounded by the master line; its icon order, sizes, and label group remain intact.

HEADER-ANCHOR INTERPRETATION
The prompt refers to a "box/checkbox" AppBar icon, while the visual TrailWeigh checkmark
is located immediately after the protected left hamburger. The feasible far-right master
anchor is the terminal moving-box identity icon, not the left title checkmark. R0092
therefore aligns the structural non-hamburger group and that terminal box to the weight
unit edge. This preserves all header controls and is specifically included in Kevin's
real-iPhone verification checklist.
