UNKNOWNS
- The original iPhone recording did not include viewport-diagnostic DOM telemetry,
  so no exact historical device-side env(safe-area-inset-top), visualViewport, or
  AppBar DOM rectangle can be claimed from the recording.
- The physical iPhone safe-top value may differ by device, orientation, and Safari UI
  state; the implementation intentionally derives it rather than assuming 20px.

ASSUMPTIONS
- The iPhone failure is the shell's layout-viewport origin being above the usable
  content origin because the fixed shell had no top safe-area placement.
- A controlled 20px custom-property override is appropriate for Chromium geometry
  validation only. It is not presented as the user's actual safe-area value.

ROOT CAUSE
The R0095/R0096 shell was fixed at top:0 with no safe-area inset. On the supplied
iPhone Safari run, its first 52px (the AppBar) lands outside the usable visible
content origin while its absolute Summary is the first visible layer. The shell
still used its complete layout height, so simply moving the shell without adjusting
its height would have displaced the locked Bottom Box Groups.

EXACT FIX
- Defined --tw-safe-top on the mobile shell from env(safe-area-inset-top, 0px).
- Positioned the shell at var(--tw-safe-top).
- Reduced shell height by that exact same inset so the shell bottom remains on the
  same physical screen line.
- Made Bottom Box Groups subtract the same inset from its layout-viewport top
  coordinate because it is an absolute child of the moved shell.
- Made Home begin at AppBar height + the same safe inset.
- No hardcoded 52px top compensation was added; the existing 52px AppBar remains
  its original height inside the safely placed shell.

THREE STANDING REPLIT QUESTIONS
1. What did you learn that improves future prompts?
   In a safe-area-shifted fixed shell, every absolute child using a layout-viewport
   top coordinate must be converted to the shell's local coordinate system; moving
   only the root would move the footer down.
2. What was unclear, unnecessary, risky, or better expressed?
   The iPhone video proves a visual failure but cannot provide exact DOM values. It
   is best paired with a viewport-diagnostic snapshot in a future report rather
   than requiring inferred physical-pixel geometry.
3. What Replit/project guidance helps next time?
   Use a route-scoped safe-area custom property so Chromium tests can simulate a
   nonzero safe inset without modifying global viewport behavior. Keep iPhone Safari
   evidence as the acceptance authority and wait for the drawer close transition
   before checking its offscreen rectangle.
