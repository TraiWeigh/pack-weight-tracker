STANDING QUESTIONS
1. What did this task teach us for future prompts?
   Fixed-layer viewport correctness and screen efficiency are separate concerns. When a
   mobile app already matches visualViewport dimensions, first measure fixed reservations,
   content capacity, and inner padding before considering any browser or root-layout fix.
   The shared CARD_H constant also controls Home bars, so checklist-only density must use
   a separate value to avoid unintentionally changing Home.

2. Was anything unclear, unnecessary, risky, or better expressed another way?
   The prompt was clear and correctly protected the Safari architecture. The one subtle
   testing consideration is fractional CSS edges: the Summary can overlap a row border by
   0.25px, so a one-pixel visual tolerance is appropriate when counting complete rows.
   Real-iPhone row-count confirmation remains necessary because Safari's chrome height is
   not reproducible in Chromium.

3. What Replit/project detail will help future work?
   Use targeted package typechecks and isolated Playwright output for TrailWeigh changes:
   the broader workspace typecheck and project-wide e2e workflow currently include
   unrelated failures. The active web artifact is root-mounted and HMR updates the running
   web workflow without a configuration change.
