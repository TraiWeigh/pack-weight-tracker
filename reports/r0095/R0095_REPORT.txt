while the page scrolls and Safari browser controls change, the TrailWeigh AppBar/title,

should move. This real-device evidence outranks all prior Chromium and CSS-fixed results.

R0094 CURRENT ARCHITECTURE — BEFORE R0095
- Scroll owner: document/window. `main-scroll` was flow content with `overflow: visible`.
- Root: normal document-flow mobile root with minimum viewport height.
- AppBar: independent CSS fixed layer at top 0.
- List Summary: independent CSS fixed layer at top 52.
- Bottom Box Groups: independent fixed layer, top derived from
  documentElement.clientHeight minus measured nav height.
- Existing long-category item viewport: bounded internal overflow scroller.
- Result: even without JavaScript scroll compensation, Safari’s document/page scroll path
  could visibly move all three separate chrome layers with browser-chrome animation.

FACTS
- The latest iPhone recording shows all three chrome layers moving during normal page
  scrolling; this is not only a footer problem.
- Before R0095, the checklist used document scrolling and the three chrome layers were
  positioned independently of an app shell.
- The existing long-category item viewport is already intentionally bounded and scrollable.
- Home already owns an internal `home-content-scroll` region.
- No source path in the final R0095 shell listens to window/document/visualViewport scroll
  to mutate chrome geometry.

UNKNOWNS
- Chromium cannot reproduce Safari’s browser-chrome compositor behavior.
- The final iPhone result still requires Kevin’s slow-scroll, flick, reverse-scroll, and
  continued-Safari-control-animation recording.

ASSUMPTION
- A route-scoped shell that prevents ordinary document motion and gives the checklist its
  own middle scroll viewport isolates TrailWeigh chrome from Safari’s page-scroll movement.
  This is structurally proven in Chromium and must be accepted on the real iPhone.

ROOT CAUSE
The core issue was scroll ownership, not one footer CSS declaration. The primary checklist
used document/window scrolling, leaving the AppBar, Summary, and footer as independent
fixed layers in Safari’s page viewport. Safari can change that page/visual geometry while
browser controls animate, so every “fixed” chrome layer could appear to drift with the
document despite stable Chromium rects.

R0095 NEW SCROLL-OWNER ARCHITECTURE
- The `/mobile-functional-v3` root is a fixed-height, overflow-hidden app shell sized from
  the stable layout viewport height.
- Route-scoped `html:has(.tw-v3-root)` and `body:has(.tw-v3-root)` overflow locking removes
  whole-document checklist scrolling without changing global application behavior.
- AppBar, List Summary, and Bottom Box Groups are absolute, non-scrolling children of that
  shell. Their preserved coordinates at 402×714 are AppBar top 0px, Summary below the
  52px AppBar, and Bottom Box Groups top 656px with 58px height.
- `main-scroll` is the only ordinary checklist/category scroll owner: flexes between the
  measured Summary and measured footer, uses `overflow-y:auto`, touch pan-y, and contained
  overscroll.
- The prior short-category pager and category-open alignment helper now update
  `mainScrollRef.scrollTop`, never window/document scroll.
- The bounded long-category item scroller is preserved; it remains an intentional nested
  item viewport inside the outer checklist viewport.
- Home is preserved with its pre-existing own internal content scroller.

STANDING REPLIT QUESTIONS
1. What did you learn?
   The decisive boundary is scroll ownership. CSS-fixed layers can still be visually wrong
   on real Safari if normal use scrolls the document. A stable app shell isolates chrome
   only when ordinary content scroll is owned by a bounded internal region.

2. Was anything unclear, unnecessary, risky, or better expressed another way?
   The R0095 direction was clear and correctly prioritized physical stability over Safari
   address-bar retraction. “Fixed” should always be stated as physical-screen behavior,
   not a CSS property or Chromium rectangle. Scoped root locking carries nested-scroll risk,
   so preserving and directly testing the existing long-category viewport was essential.

3. What project detail helps future work?
   Mobile V3 now intentionally has three scroll modes: outer checklist `main-scroll`,
   bounded long-category item scrolling, and Home content scrolling. Do not reintroduce
   document scrolling for ordinary checklist navigation; assert main scroll changes while
   window/document/body remain zero, then validate the result on real iPhone Safari.
