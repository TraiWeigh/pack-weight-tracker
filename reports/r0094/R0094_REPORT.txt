IPHONE DIAGNOSTIC CONTEXT
Earlier real-device measurement reports the iPhone layout/document client height remained
about 714px while Safari’s usable visual viewport / innerHeight could grow about 714→754px
as browser chrome compacted. A footer anchored to `bottom: 0` follows that changing bottom
edge. The AppBar and Summary do not have the same failure because their top coordinates
remain on a stable screen line.

ROOT CAUSE
R0093 removed JavaScript compensation but retained `position: fixed; bottom: 0`. On the
actual iPhone Safari path, that bottom anchor is still tied to the dynamic visual-viewport
bottom, so the footer moves downward/upward with browser-chrome animation. The failure was
not an application scroll handler or transform; it was the footer using a different
coordinate philosophy than the top fixed layers.

R0094 CORRECTION
- Bottom Box Groups remains a fixed viewport layer but is now positioned by a responsive
  `top` coordinate, not the dynamic `bottom` edge.
- The coordinate is `document.documentElement.clientHeight − measured footer height`.
  At the 402×714 reference layout, that is `714 − 58 = 656px`.
- `documentElement.clientHeight` is captured at startup and re-read through a
  ResizeObserver only when the layout viewport itself changes. That preserves genuine
  responsive/orientation behavior without listening to ordinary document or
  visual-viewport scroll events.
- The footer's authored CSS is `position: fixed; top: <stable layout top>; bottom: auto`.
  Chromium resolves the computed bottom value to `0px` for this geometry, so tests inspect
  the authored inline `bottom: auto`, the authored top, the stable-top marker, and rendered
  rect instead of misinterpreting that browser-resolved shorthand.
- The measured footer height remains the sole content/deck reservation. Native document
  scrolling, list geometry, and all horizontal layout remain unchanged.

STANDING QUESTIONS FOR REPLIT
1. What did this teach us?
   Removing JavaScript scroll compensation is not sufficient when a fixed bottom anchor
   itself follows Safari’s dynamic visual viewport. In document-scrolling mobile layouts,
   compare both coordinate direction and viewport reference with stable top layers before
   deciding a footer is locked.

2. What could be expressed better?
   “Fixed” must be defined as physical-screen stability, not merely CSS `position: fixed`
   or a stable Chromium DOM rect. The iPhone diagnostic pairing of clientHeight and
   visualViewport height is the essential acceptance evidence for this class of issue.

3. What project detail helps future work?
   The active mobile checklist intentionally uses native document scrolling. Keep the
   footer outside moving content, preserve the measured footer-height reservation for
   content/decks, and use focused Playwright geometry tests as structural evidence while
   reserving Safari compositing acceptance for real device recording.
