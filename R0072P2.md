## Drag/Release Activation (Test C)

Drag: pointer down, moved **110 px upward** (> `DRAG_ACTIVATE = 48 px` threshold), then released.

| State | Observation |
|---|---|
| Active before drag | None — all 4 bars stacked |
| Active after drag/release | "List Actions" card is **no longer findable** as a stacked bar |
| `getByRole('button', { name: 'List Actions — open card' })` after release | Element **GONE** from DOM |
| Transform after release | Element gone — cannot measure |
| Bars remaining in stacked state | Unknown (element gone) |

**Evidence for activation:** After the 110 px drag and release, any attempt to locate the "List Actions — open card" stacked-bar element via `getByRole` or `evaluate` fails with a timeout — the element is no longer in the stacked-bar DOM position. This is consistent with the source code's `onActivate()` call having fired, which removes the `DeckInactiveCard` from the DOM and renders the active-card content instead.

The source code (line 1033–1034 of `MobileFunctionalV3.tsx`) confirms:
```ts
if (mode === 'lift' && lifted >= DRAG_ACTIVATE) { setLift(0); onActivate(); return; }
```
`DRAG_ACTIVATE = 48`. A drag of 110 px ≫ 48 px. `onActivate()` fires during pointer movement (not on release), removing the stacked bar from the DOM.

**TEST C RESULT: FAIL — drag/release (at ≥ 48 px) activates the stacked bar.**

**−80.00 px** (upward). Scroll-adjusted: **−80.00 px** (parent scrollTop = 0 throughout).

**Q9. Did computed transform change?**
**YES.** Before: `matrix(1, 0, 0, 1, 0, 0)` (identity). During: `matrix(1, 0, 0, 1, 0, -80)` (translateY(−80px)).

**Q10. Did the target visibly lift/follow the finger?**

**Q14. Is the user requirement "stacked bars must not move" currently PASS or FAIL?**
**FAIL.** The bar physically moves upward (by the exact drag amount in px) and also activates on a sufficient drag.

**Q15. If FAIL, what is the smallest safe correction?**
*(READ-ONLY — not implemented)*

**Option A — Remove lift mode entirely (smallest change):**
In `DeckInactiveCard.onPointerMove`, change the mode-locking expression from:
```ts
d.mode = canDeckScroll() ? 'scroll'
  : (totalDy < 0 && !card.disabled ? 'lift' : 'scroll');
```
to:
```ts
d.mode = 'scroll';
```
This makes all inactive bars use scroll mode only. Upward drag on a non-overflowing deck does nothing (no scroll needed = no-op). Bars are tap-only. The drag-to-dock gesture disappears entirely.

**Option B — Keep drag-to-dock but suppress visual lift (medium change):**
Remove `setLift(startY - e.clientY)` from the `'lift'` branch (line 1078), while keeping the `lifted >= DRAG_ACTIVATE → onActivate()` activation check. This lets the user drag-to-activate without the bar visually following the finger. The bar activates "invisibly" after a sufficient upward drag. The visual lift is gone but the gesture still works.

**Recommendation:** Option A (remove lift mode). The drag-to-dock gesture was added as a power-user shortcut, but the spec says stacked bars must not move. Tap-only navigation is clearer UX for stacked bars.

**Q16. What exact application file(s) would need to change?**
`artifacts/pack-checklist/src/pages/MobileFunctionalV3.tsx` — specifically the `DeckInactiveCard.onPointerMove` handler around line 1071.

**Q17. Which already-working R0072 behaviours are at risk from that correction?**
- No R0072 test checks for drag-to-activate on stacked bars. Removing lift mode would cause no R0072 test regressions.
- The `DeckInactiveCard` keyboard handler (`Enter`/`Space` → `onActivate`) is unaffected.
- Normal tap (click) on stacked bars is unaffected — it bypasses `onPointerMove` entirely.
- All 60 R0072 tests would continue to pass after Option A or Option B.
