2. DIAGNOSE THE PASSWORD RECOVERY FAILURE
==================================================

The user reports that the password/recovery process has not been working
correctly.

Determine the REAL root cause.

Do not guess.

Investigate whether the problem is caused by:

A. Incorrect password verification logic

B. Broken reset-token or reset-email flow

C. Reset appears successful in the UI but the new password is not actually
   stored

D. Session/auth state remains stale after reset

E. Wrong authentication endpoint/provider method is being called

F. The account actually uses Google sign-in rather than password sign-in

G. The account uses passwordless email/email-code authentication

H. Multiple authentication providers exist for the same account

I. Attempt/rate-limit logic is incorrect

K. Error handling is hiding the actual problem

==================================================

Inspect the warning:

"There are only 2 remaining attempts."

Verify whether:

- Only a genuine failed password authentication attempt decrements it

rate-limit protections.

==================================================
5. PASSWORD RESET SUCCESS / FAILURE FEEDBACK
==================================================

The recovery flow must clearly tell the user what happened.

If reset initiation succeeds:

Make the next step clear.

If a reset email/code/link was sent:

Say so clearly.

If the password is successfully changed:

Display a clear success state/message.

Then direct the user to the correct next step.

If password authentication is supported:

The newly created password must actually work.

If the account does not support password authentication:

Guide the user to the correct Google/email-code method instead.

Avoid:

- Silent failure
- Generic "Something went wrong" messaging when a safe specific explanation
  is possible
- Internal stack traces
- Sensitive authentication details
