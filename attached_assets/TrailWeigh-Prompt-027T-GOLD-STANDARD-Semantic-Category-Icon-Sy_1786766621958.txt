category symbol exists.

============================================================
DESIGN GOAL
============================================================

Create ONE reusable semantic category-icon resolver/mapping system.

It should be capable of receiving a category name and returning the best
available icon deterministically.

Conceptually:

`getCategoryIcon(categoryName, context?)`

Exact name/implementation may differ.

Requirements:
- deterministic
- semantic
- extensible
- readable
- does not scatter hard-coded icon decisions throughout V3 markup
- easy to add synonyms later
- supports existing categories and future custom categories

============================================================
DUPLICATE-AVOIDANCE RULE
============================================================

Within one visible list:

1. Prefer the best semantic icon.
2. If two different categories resolve to the SAME icon:
   - check whether an equally meaningful alternative exists for one category
   - use the alternative where practical
3. Do not sacrifice semantic clarity merely to force uniqueness.
4. If no meaningful alternative exists:
   - duplicate is allowed
   - report the conflict

Example:
`Electronics` and `Chargers & Cables` should not both be forced to Lightning
if Plug/Cable is available for the latter.

============================================================
STABILITY RULE
============================================================

A category should not randomly change icons between renders.

Icon selection must be deterministic for the same category name and context.

Renaming a category may intentionally cause semantic remapping.

If user creates:
`Dog Gear`
it should resolve consistently to a dog/paw/pet symbol.

If renamed:
`Electronics`
it should resolve consistently to electronics.
