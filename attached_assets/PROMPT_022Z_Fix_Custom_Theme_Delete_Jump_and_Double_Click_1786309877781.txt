==================================================
1. EXACT BUG TO FIX
==================================================

Current incorrect behavior:

TRASH CLICK
→ confirmation appears correctly beside trash

FIRST "DELETE THEME" CLICK
→ Background panel closes
→ confirmation remains mounted
→ anchor/trigger disappears
→ confirmation jumps to top-left
→ deletion not fully completed

SECOND "DELETE THEME" CLICK
→ deletion completes

The final implementation must eliminate this sequence.

==================================================
2. REQUIRED FINAL BEHAVIOR
==================================================

Correct sequence:

A. Click trash icon.

Expected:
- delete confirmation opens beside that trash icon
- Background Edit panel stays open

B. Click "Delete Theme" ONCE.

Expected:
- selected custom theme is deleted immediately
- confirmation closes
- deleted theme disappears
- Background panel may remain open unless the existing product behavior
  intentionally closes it AFTER deletion
- no second confirmation appears
- no second click is required
- nothing jumps to the upper-left corner

ONE CONFIRMATION CLICK = ONE COMPLETED DELETION.

==================================================
3. DO NOT UNMOUNT THE ANCHOR BEFORE CONFIRMATION COMPLETES
==================================================

The video strongly suggests that the trash trigger or its containing
Background panel is being unmounted before the delete action finishes.

Inspect this carefully.

Do NOT close/unmount:
- Background Edit panel
- selected custom-theme row
- trash trigger
- popover anchor/reference

BEFORE the confirmation handler has completed the deletion and closed the
popover.

Safe sequence should be conceptually:

1. user confirms deletion
2. capture/retain target theme ID
3. execute delete action
4. confirm state update succeeds
5. close delete popover
6. update/remove deleted theme row
7. only then perform any optional panel-state change

Do not rely on a DOM anchor that has already been destroyed.

==================================================
4. PENDING DELETE TARGET MUST BE STABLE
==================================================

When the trash button is clicked, retain the target custom-theme ID in stable
state.

Example concept:

pendingDeleteThemeId

or equivalent.

The Delete Theme button must delete that stored ID.

It must NOT depend on:
- whatever theme happens to remain selected after the panel closes
- a DOM element still existing
- current hover state
- a second click
- recalculating the target after the first confirmation click

Clear the pending-delete target only AFTER:
- deletion completes, OR
- user cancels.

==================================================
5. POPOVER MUST CLOSE, NOT RE-ANCHOR TO 0,0
==================================================

If the anchor/trigger becomes unavailable for any reason:

The popover must CLOSE.

It must NEVER remain visible at a fallback coordinate such as:
- top: 0
- left: 0
- upper-left page corner

There should be no visual state where the confirmation floats detached from
its trash icon.

If the popover library loses its reference element:
- close the popover
- do not render it at a default/fallback page coordinate

==================================================
6. CONFIRM BUTTON EVENT HANDLING
==================================================

Inspect the "Delete Theme" button event.

Verify it does not accidentally:

- trigger the parent Background Edit button
- bubble into a panel close handler
- trigger an outside-click handler before deletion
- fire onPointerDown that closes the panel before onClick
- submit an unrelated form
- activate a second click target underneath after unmount
- call close first and delete later in a way that destroys required state

Use appropriate:
- event ordering
- propagation control
- popover event handling

only where needed.

Do not blanket stopPropagation everywhere.

==================================================
7. ASYNC DELETE ORDER
==================================================

If deleteTheme() is asynchronous:

Use an explicit sequence.

Expected concept:

await deleteTheme(targetThemeId)

then:
- close confirmation
- clear pending delete target
- update UI

If the existing delete function is synchronous:
- still preserve the same logical order.

Do not close/unmount the anchor before the delete call has the stable theme ID.

==================================================
8. BACKGROUND PANEL BEHAVIOR
==================================================

The preferred behavior is:

After successful custom-theme deletion:
- keep Background Edit open
- show the remaining theme list
- allow the user to continue editing backgrounds

This is less disruptive and avoids destroying the popover hierarchy during the
delete action.

If there is a strong existing product reason that the Background panel must
close after deletion:

It may close ONLY AFTER:
- deletion is complete
- confirmation is closed
- no unanchored popover remains

Document the final behavior.

- cause the popover to jump
- recreate the deleted theme
