============================================================
PART A — CORRECT CONFIRMED R002Q DEFECTS
============================================================

A1. LOCKER / LONG-DECK TOUCH SCROLLING — FUNCTIONAL BLOCKER

R002Q confirmed:
- inactive cards use touch/pointer handling that prevents native vertical scrolling;
- upward drag is interpreted as activation;
- downward drag only decreases scrollTop;
- with long Locker decks, later saved-list cards become unreachable;
- intended upward scroll can accidentally activate/dock a card.

REQUIRED RESULT
A long deck containing 10, 20, or more entries must be reliably scrollable with one finger in BOTH directions.

The interaction must distinguish:
1. tap;
2. deck scrolling;
3. intentional card/bar activation drag.

Requirements:
- Vertical scrolling through an overflowing deck must work naturally in both directions.
- A normal scroll gesture must NOT accidentally activate/dock a bar.
- Tap must always remain an activation alternative.
- Drag activation may remain, but it must not hijack normal scroll.
- The user must be able to reverse direction naturally.
- No dead scrolling direction.
- Do not rely on inaccessible gaps between bars to make scrolling possible.
- Do not make dragging the only way to activate.
- Do not create bounce/overshoot.
- Keep reduced-motion behavior.

Choose a robust gesture-disambiguation strategy appropriate to the existing V3 architecture.
Do not merely lower/raise thresholds while leaving the fundamental scroll-versus-activation conflict unresolved.

TEST WITH A GENUINELY OVERFLOWING TEMPORARY DECK.
Use temporary test-only/mock entries if needed.
Do not persist diagnostic entries to real app data.

A2. LOCKER ACTIVE LIST NAME / IDENTITY SYNCHRONIZATION

R002Q confirmed:
- loading a Locker entry replaces the list contents;
- the centered/current list name state is not updated;
- Save and Share can therefore continue using the OLD list name after loading another list.

REQUIRED RESULT
When a Locker file/list is loaded:
- the active list name must immediately become the loaded Locker entry's name;
- the user-facing title/file identity must reflect the loaded file;
- subsequent Save and Share must use the correct loaded list name;
- do not alter the Locker storage architecture;
- do not create a new database/storage model.

This should remain a narrow V3 state-synchronization correction.

A3. DISABLED SEARCH / DISABLED DECK-BAR READABILITY

R002Q confirmed:
- disabled deck entries currently fade the entire surface;
- the underlying category/list content bleeds through;
- text visually collides.

REQUIRED RESULT
Disabled deck bars must remain fully opaque as structural surfaces.

Only the disabled CONTENT should appear muted:
- icon;
- title;
- subtitle/status;
- other disabled foreground content.

Do NOT fade the entire bar background.
Do NOT let the active list behind the deck show through disabled bars.

This rule should apply consistently to any disabled deck entry, including future/unavailable Search entries and disabled Create New List if present.

A4. SAFE AREA / HOME-INDICATOR CLEARANCE

R002Q confirmed:
- the bottom nav can grow with safe-area inset;
- deck/backdrop offsets were based on a fixed 58 px constant;
- on a device with a nonzero bottom safe-area inset, active deck controls can sit behind the nav.

REQUIRED RESULT
The deck, backdrop, and bottom navigation must share one correct source of truth for the actual bottom occupied area.

On a phone with a home-indicator safe area:
- no part of the active deck controls may be covered by the bottom nav;
- no deck content may sit behind the bottom nav;
- no backdrop gap should appear;
- bottom navigation remains safe-area compliant.

Use a robust safe-area-derived offset or measured rendered nav height.
Do not rely on the old fixed 58 px offset if the nav's actual occupied height can differ.

Provide a meaningful proof test for a NONZERO inset condition, not only normal desktop Playwright where env(safe-area-inset-bottom) resolves to zero.

PART B — NEW APPROVED MOBILE VISUAL LANGUAGE
============================================================

B1. ACTIVE LIST REMAINS THE RESTING SCREEN

The active list is always the underlying/main phone workspace.

There is NO permanent List bottom button in R003.

When no deck is open:
- show the active list normally;
- preserve its scroll position;
- preserve category accordion state;
- preserve selected/check state;
- preserve quantity/weight/unit state;
- preserve undo/redo history;
- preserve active list identity.

B2. BOTTOM NAVIGATION — EXACT FIVE AREAS

Change the permanent bottom navigation to:

LOCKER | SUMMARY | ADD | SEARCH | MORE

Rules:
- five touching square-edged bottom boxes;
- no gaps between boxes;
- no rounded outer corners;
- no floating circular Add button;
- Add remains the center area;
- each area has a clear icon;
- concise label where the current V3 design needs one for clarity/accessibility;
- active/open state is visually clear but restrained;
- all controls remain thumb-friendly;
- safe-area compliant.

Interaction:
- tap Locker -> Locker deck opens;
- tap Locker again -> Locker deck closes and reveals the active list;
- tap Add while Locker is open -> switch directly from Locker deck to Add deck;
- tap Add again -> Add closes;
- same open/toggle/switch behavior for Summary, Search, More;
- no intermediate requirement to return to the list before switching decks.

Do NOT add a List tab.

B3. TOP SEARCH CONTROL

DO NOT remove the existing older top Search circle/control in R003.
Its removal is a separate user-approval decision.
Do not change its behavior.

B4. PACK SUMMARY + FILE/LIST NAME

Remove the separate standalone file-name strip/pill/bar in V3.

Integrate the active file/list name into the Pack Summary structural bar.

Required appearance:
- one combined File Identity + Pack Summary structural region;
- square-edged;
- flush;
- no rounded outer corners;
- no outer card margin;
- no redundant separate file-name region;
- keep useful internal padding so text does not touch edges;
- active file/list name must be clearly readable;
- loading from Locker must update this integrated name immediately.

Do NOT eliminate important Pack Summary information merely to save space.
Use clear typography hierarchy inside the combined structural bar.

B5. CATEGORIES — FLUSH STRUCTURAL STACK

Preserve category wedges.

Refine the category stack:
- remove outer spacing/gaps around category blocks;
- category structural bars stack flush/touching;
- square outer edges;
- no rounded outer corners on the main category structural surfaces;
- visually harmonize with the bottom bar;
- do not add thick heavy borders;
- use subtle dividers/surface-tone differences/typography/wedges for separation;
- retain enough INTERNAL padding for readable text/icons and comfortable touch targets.

"Everything touching" means remove EXTERNAL gaps.
It does NOT mean text/icons should touch edges.

Do not make expanded category item content unusably cramped.
The user still needs comfortable tapping and scanning.

B6. NO VISIBLE SCROLLBAR CHROME

Preserve normal scrolling.

Hide visible scrollbar track/thumb chrome on the intended phone V3 surfaces where practical.

Requirements:
- list still scrolls;
- long decks still scroll;
- no permanent right-side scrollbar visually occupying space;
- do not disable scrolling to hide the scrollbar.

B7. COMPACT STACKED-BAR DECK GEOMETRY

The R002 large rounded Wallet-card look is superseded.

Keep the stacked/deck interaction, but make each deck item approximately the SAME VISUAL SCALE / HEIGHT FAMILY AS A CATEGORY HEADER BAR.

Deck items are now compact "stacked bars."

Required:
- square-edged rectangular bars;
- no large credit-card proportions;
- no fake bank-card visual language;
- no rounded outer corners;
- bar-height / category-header-like proportions;
- clear icon + title;
- enough exposed area of inactive stacked bars to identify each one;
- restrained surface-tone/depth separation;
- visually part of the same TrailWeigh system as category bars and bottom nav.

The cards/bars may still overlap slightly in the stacked state if needed for the deck behavior.

They must remain:
- tappable;
- draggable where appropriate;
- readable;
- accessible;
- vertically scrollable when numerous.

B8. DECK OPEN / ACTIVE / SWITCH BEHAVIOR

For Locker, Summary, Add, Search, More:
- deck rises from bottom;
- tap or intentional drag can activate an entry;
- inactive entries remain identifiable;
- tapping another exposed entry switches directly;
- tapping the same bottom area closes its deck;
- tapping another bottom area switches decks directly;
- active list state underneath must not reset.

During intentional drag:
- direct finger tracking where practical;
- reverse direction allowed;
- smooth settle after release;
- no uncontrolled spring/bounce/overshoot;
- no accidental destructive swipe;
- reduced motion respected.

If supported legitimately:
- one restrained haptic when an entry docks/activates;
- no continuous vibration;
- no fake haptics.
