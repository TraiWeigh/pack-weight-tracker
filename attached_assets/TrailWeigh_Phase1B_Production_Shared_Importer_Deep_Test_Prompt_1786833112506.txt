TRAILWEIGH — PLAYWRIGHT DEEP TESTING PHASE 1B
PRODUCTION-SHARED FUNCTIONALITY + IMPORTERS + COVERAGE GAPS

MODE: Power
PLAN MODE: OFF
APP TESTING: OFF WHILE PLAYWRIGHT IS RUNNING

PURPOSE

Extend TrailWeigh's permanent Playwright regression system beyond the isolated
/mobile-functional-v3 sandbox and into production-shared functionality that can
be tested safely WITHOUT using a real owner's account or modifying real user data.

This Phase 1B exists because the post-Phase-1 capability audit proved that
/mobile-functional-v3 is a useful isolated sandbox, but it does NOT represent
all real TrailWeigh production behavior.

This prompt must:
- test production-shared logic where safe,
- close the most important Phase 1 coverage gaps,
- test importers using safe local fixtures,
- test Review/shared behavior with mocked/disposable data where possible,
- test failure handling,
- FIND and DOCUMENT bugs,
- NOT repair application bugs.

==================================================
0. CRITICAL STANDING RULES
==================================================

DO NOT:
- modify TrailWeigh application source code,
- repair TW-P1-001, TW-P1-002, TW-P1-003,
- weaken existing tests to turn failures green,
- use the user's real TrailWeigh account,
- use production credentials,
- create persistent real-owner data,
- create real public shares unless a separate safe test architecture already exists,
- modify database/schema/authentication,
- install Firefox or WebKit,
- add Axe/Lighthouse/Sentry/security tooling,
- begin visual regression,
- change playwright.config.ts without stopping and asking first,
- run Replit App Testing concurrently with Playwright.

IMPORTANT RESOURCE RULES:
- Playwright worker count: 1.
- Run tests in foreground.
- Split long execution into deterministic chunks intended to finish in roughly 4 minutes or less.
- Do not use nohup/background execution for the actual audit.
- Do not start multiple Playwright runs simultaneously.
- Avoid unnecessary repeated source scans.
- Reuse evidence already established by the capability audit.
- Be surgical with file reading and actions.

If a test area cannot be tested safely under these rules:
classify it as BLOCKED / NEEDS AUTHENTICATED TEST ARCHITECTURE and continue with independent safe areas.

==================================================
3. REQUIRED PHASE 1B TEST AREAS
==================================================

Build safe Playwright coverage for every feasible area below.

--------------------------------------------------
A. REVIEW / SHARED PAGE — SAFE MOCKED COVERAGE
--------------------------------------------------

Test the real Review/shared page code path using controlled mocked share data
or another read-only/disposable mechanism already supported by the app.

Do NOT create real shares on real accounts.

Cover where safely possible:

1. Review route loads.
2. Shared list data is rendered.
3. File/list name is shown.
4. Categories render.
5. Items render.
6. Main category accordion behavior.
7. Expand All / Collapse All.
8. Sidebar/panel behavior if present.
9. Unit display/switching if available.
10. Editing in Review sandbox does not invoke owner-mutating API calls.
11. Local Review edits remain within Review sandbox.
12. Reload behavior matches current Review design.
13. Owner-only controls/data are absent/inaccessible.
14. No owner Locker/files are exposed.
15. Failed share fetch produces safe user-facing behavior.
16. 404/invalid token behavior.
17. 500 behavior.
18. Slow response behavior.
19. Dropped request behavior.

If mocking the Review route would require changing production source:
STOP that sub-area and report the blocker.

--------------------------------------------------
B. PRODUCTION-SHARED ITEM EDITING / CALCULATIONS
--------------------------------------------------

Where the real ChecklistContent or production-shared components can be mounted
or reached safely without a real account, test:

1. Item name edit.
2. Item Type edit if current product supports it.
3. Quantity edit.
4. Weight edit.
5. Unit switch.
6. Selected/not-selected state if applicable.
7. Category totals.
8. Overall/list totals.
9. Repeated unit conversion and return.
10. Decimal weights.
11. Qty > 1.
12. Zero weight where allowed.
13. Invalid negative attempt.
14. No NaN / Infinity / undefined displayed.
15. Editing one item does not mutate another.
16. Move item between categories if the Move control is available and safe.

Where authenticated persistence blocks safe testing:
test the production-shared UI/state logic without persisting to the backend,
or classify the backend portion separately as NEEDS AUTHENTICATED TEST ARCHITECTURE.

--------------------------------------------------
C. ITEM MOVE
--------------------------------------------------

Phase 1A did not actually exercise the visible Move control.

Test, where safe:

1. Move item from Category A to Category B.
2. Item disappears from A.
3. Item appears in B.
4. Item data remains unchanged.
5. Counts/totals update correctly.
6. Moving back works.
7. Invalid/no-op selection does not duplicate the item.
8. Move does not create a second copy.
9. Undo/Redo behavior if Move currently participates in history.

If the Move control exists only in sandbox or differs in Owner code:
test each safe implementation separately and label them accurately.

--------------------------------------------------
D. CATEGORY REORDER / DRAG FEASIBILITY
--------------------------------------------------

Phase 1A inventoried reorder but did not test it.

First perform a TESTABILITY check without app changes.

Determine whether the current reorder interaction can be automated reliably with:
- mouse drag,
- pointer events,
- keyboard alternative if available,
- existing accessible controls.

If reliable:
test bounded category reorder:
1. move one category,
2. verify new order,
3. verify category contents remain attached,
4. verify totals unchanged,
5. reload/persistence only where safe and expected.

If unreliable:
do NOT create a brittle test merely to claim coverage.
Report:
NOT RELIABLY AUTOMATABLE YET
and exact reason.

--------------------------------------------------
E. PRINT
--------------------------------------------------

Test the current Print control if safely reachable.

Cover:
1. control exists and is enabled where expected,
2. triggering Print calls the browser print path / print event or equivalent,
3. it does not navigate away or corrupt state,
4. no JS/page error,
5. Print action can be intercepted/stubbed so no real printer dialog blocks the test.

Do NOT perform visual print-layout comparison in Phase 1B.

--------------------------------------------------
F. TOOLTIPS / HELP / KEYBOARD
--------------------------------------------------

For a representative cross-section of CURRENT interactive controls:

1. keyboard focus reaches the control,
2. Enter/Space activates where appropriate,
3. tooltip/help appears on hover/focus where current product supports it,
4. tooltip does not block activation,
5. accessible name exists,
6. icon-only controls can be understood through accessible name/tooltip,
7. Escape closes temporary overlay/popup where expected,
8. Tab order does not get trapped in a basic core workflow.

Do not attempt full WCAG testing here; Axe comes later.

Record any control that is impossible to target reliably due to missing accessible labeling.

--------------------------------------------------
G. PDF IMPORTER
--------------------------------------------------

Use SAFE LOCAL FIXTURES only.

Search the repository/workflow test assets for an existing known 77-item PDF regression fixture.
Do NOT download replacement fixtures from the internet.

If the exact known 77-item fixture exists:
test:
1. import starts,
2. parser completes,
3. exact item count = 77,
4. category totals/counts match the known regression expectations if those expectations are available in repository reports/fixtures,
5. no item loss,
6. no duplicate rows,
7. no Big Three/Bits regression where applicable,
8. Description→Name behavior where represented,
9. Worn routing where represented,
10. preview loads,
11. no uncaught page error.

If the exact fixture is not available:
state BLOCKED — FIXTURE NOT PRESENT.
Do not fabricate the expected 77-item file.

Also test small safe PDFs if existing fixtures are available.

--------------------------------------------------
H. CSV IMPORTER
--------------------------------------------------

Use local fixture files under test-only fixture directories.

Cover representative cases:
1. normal valid CSV,
2. accepted heading variants if existing behavior supports them,
3. Category,
4. Type,
5. Description/Name,
6. Qty,
7. Weight,
8. Worn status if supported,
9. missing optional field,
10. empty file,
11. malformed row,
12. Unicode item name,
13. duplicate names,
14. zero quantity attempt if accepted,
15. invalid numeric weight,
16. preview behavior,
17. row count preservation,
18. no uncaught error.

Do not redefine parser business rules.
Use current code/reports as truth.

--------------------------------------------------
I. DOCX IMPORTER
--------------------------------------------------

Use local fixture files only.

Cover existing supported behavior:
1. Heading 1/2 category context,
2. plain bold Normal headings if existing fixtures exist,
3. bullet-list-only DOCX if fixture exists,
4. Description→Name behavior,
5. category routing,
6. malformed/empty DOCX where safely testable,
7. Unicode,
8. no silent row loss,
9. no uncaught exception.

If fixture coverage is unavailable:
report exact missing fixture rather than inventing expected behavior.

--------------------------------------------------
J. IMPORTER MALFORMED / FAILURE HANDLING
--------------------------------------------------

For PDF/CSV/DOCX where safe:

Test:
- empty file,
- wrong extension/content mismatch where reasonable,
- malformed content,
- unsupported columns/headings,
- parser error,
- oversized-but-reasonable test file only if existing fixture exists,
- cancelled import if UI supports cancel,
- failed network request if importer uses backend API.

Expected:
- no app crash,
- no frozen overlay,
- clear error/warning,
- user can recover,
- no partial persistent owner mutation.

--------------------------------------------------

--------------------------------------------------

- timeout,
- HTTP 400,
- 401,
- 403,
- 404,

- 500,
- slow response,
- aborted/dropped request.

Prioritize:

Verify:
- no uncaught crash,
- safe user-facing state,
- retry/recovery where supported,
- no infinite spinner,
- no destructive mutation.

==================================================
6. FAILURE HANDLING
==================================================

Do not stop the whole audit after one independent app defect.

For each failed test:

1. rerun that single test once in isolation,
2. classify:
   - REPRODUCIBLE APPLICATION DEFECT
   - TEST INFRASTRUCTURE
   - ENVIRONMENT
   - POSSIBLY FLAKY
   - PRODUCT REQUIREMENT UNCERTAIN
3. do not repair application code,
4. do not weaken the assertion merely to pass.

If the test itself is demonstrably incorrect:
you may fix TEST CODE only,
document the correction,
rerun,
and continue.
