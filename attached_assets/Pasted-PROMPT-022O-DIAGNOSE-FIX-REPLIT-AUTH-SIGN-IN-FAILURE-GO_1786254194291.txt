PROMPT 022O — DIAGNOSE & FIX REPLIT AUTH SIGN-IN FAILURE

GOAL

Diagnose and fix a TrailWeigh authentication problem involving Replit Auth.

USER-TESTED PROBLEM

The user can successfully sign in to Replit.com with the same account.

However, TrailWeigh does not successfully recognize/complete the same login.

Therefore:

- Do NOT assume the user's password is wrong.
- Do NOT reset the user's Replit account.
- Do NOT build a separate TrailWeigh password system.
- Do NOT store or validate Replit passwords inside TrailWeigh.

This prompt is specifically about the existing Replit Auth integration.

==================================================
0. BACKUP / CHANGE PROTECTION
==================================================

Before changing anything:

1. Create the normal Replit checkpoint/backup.

2. Inspect the current authentication architecture.

3. Identify:
   - Which Replit Auth package/service is being used
   - Which routes/components start authentication
   - Which callback/redirect route completes authentication
   - Where session/user state is stored
   - How auth cookies/tokens are handled
   - How the app determines whether the user is signed in

4. Review the final diff before completion.

5. Revert unrelated changes.

6. Do NOT refactor unrelated application code.

7. Preserve:
   - Saved TrailWeigh files
   - Locker data
   - Shared links
   - Shared snapshots
   - Backgrounds
   - Checklist state
   - Weight calculations
   - All recent UI fixes

==================================================
1. DO NOT IMPLEMENT PASSWORD VALIDATION
==================================================

TrailWeigh should not validate the user's Replit password itself.

Do NOT:

- Add a TrailWeigh password database
- Hash/store Replit passwords
- Compare user passwords inside TrailWeigh
- Create a custom password workaround
- Add hardcoded credentials
- Bypass Replit Auth security

The authentication provider remains Replit Auth.

==================================================
2. TRACE THE ENTIRE AUTH FLOW
==================================================

Inspect the full sign-in path from beginning to end.

Trace:

1. User opens TrailWeigh Sign In.
2. User chooses the applicable Replit-supported authentication method.
3. TrailWeigh invokes Replit Auth.
4. Replit authenticates the user.
5. Replit returns/callbacks to TrailWeigh.
6. TrailWeigh receives the authenticated identity.
7. TrailWeigh creates/restores the application session.
8. User is recognized as signed in.
9. User is redirected to the correct TrailWeigh page.

Document the exact point where the current flow fails.

==================================================
3. CHECK REPLIT AUTH CONFIGURATION
==================================================

Inspect all current Replit Auth configuration.

Verify:

- Client/application configuration
- Callback URL
- Redirect URL
- Allowed origins
- Replit development URL
- Deployment/public URL if configured
- Environment variables/secrets required by Replit Auth
- Session secret/configuration
- Any expected issuer/audience values
- Any auth middleware configuration

Do not expose secret values in the workflow report.

It is acceptable to report:

"AUTH_SECRET present"

Do NOT print the actual secret.

==================================================
4. DEVELOPMENT VS DEPLOYMENT URLS
==================================================

TrailWeigh is currently being tested through Replit.

Verify that authentication is not failing because the callback is configured
for one URL while the user is accessing another.

Examples to inspect:

- replit.dev preview/development URL
- deployed TrailWeigh domain
- alternate development hostname
- http vs https
- trailing slash differences where relevant

The callback must return to the actual current TrailWeigh origin accepted by
the auth configuration.

Do NOT simply hardcode the user's current temporary URL if the existing
architecture supports environment-aware callback URLs.

==================================================
5. SIGN-IN METHOD
==================================================

Inspect how Replit Auth represents the user's sign-in method.

The TrailWeigh screen currently offers authentication choices such as:

- Continue with Google
- Email-based sign-in

Determine whether TrailWeigh is incorrectly assuming that every Replit
account has a separate email/password credential.

If the user originally authenticates with Google or another Replit-supported
identity provider, TrailWeigh must allow the appropriate Replit Auth method
instead of trying to interpret that as a TrailWeigh password.

Do not change account-provider relationships.

==================================================
6. CALLBACK HANDLING
==================================================

Inspect the auth callback route carefully.

Verify:

- Callback route is reachable.
- Callback parameters are read correctly.
- Authentication result is validated correctly.
- Errors are not swallowed.
- User identity is extracted correctly.
- Session establishment occurs before redirect.
- Redirect happens only after authentication completes.

Look for:
- stale callback code
- wrong callback path
- malformed redirect URL
- race condition
- callback running twice
- missing await
- session not committed before redirect
- callback errors hidden by generic "invalid password" UI

==================================================
7. SESSION / COOKIE HANDLING
==================================================

Inspect the TrailWeigh authentication session.

Verify:

- Session cookie is actually created.
- Cookie domain/path are appropriate.
- Secure flag is appropriate.
- SameSite configuration does not block the Replit Auth callback.
- HttpOnly configuration remains secure.
- Session survives redirect.
- Session survives normal page navigation.
- Browser refresh keeps user signed in when intended.

Safari must be tested because the user is using Safari.

Do not weaken cookie security unnecessarily.

==================================================
8. SAFARI-SPECIFIC CHECK
==================================================

Because the user is testing in Safari, inspect whether the issue could involve:

- SameSite cookie handling
- third-party/cross-site cookie restrictions
- redirect handling
- storage access
- popup flow
- origin mismatch

Prefer a standards-compliant first-party callback/session architecture.

Do not add browser hacks unless the root cause specifically requires a
standards-compliant Safari adjustment.

==================================================
9. ERROR MESSAGE ACCURACY
==================================================

Inspect the current error shown when sign-in fails.

If TrailWeigh displays wording such as:

- Incorrect password
- Password not recognized

but TrailWeigh is not actually validating a password, change the wording.

Use an accurate general auth error such as:

"Sign-in could not be completed. Please try again."

or, where the actual provider error is safely available:

"Replit sign-in could not be completed."

Do not expose internal stack traces or security-sensitive details.

The UI must not falsely tell users their password is wrong when the failure
occurred later in the Replit Auth/session flow.

==================================================

==================================================

Preserve:

- Visible input borders
- Readable placeholders

- Focus treatment
- Light/Dark appearance

022O is an auth-function fix, not another visual redesign.

==================================================
11. DO NOT DELETE USERS OR DATA
==================================================

- create a replacement account

- clear Locker data

  documented

Existing user-to-file ownership relationships must remain intact.

==================================================
12. USER IDENTITY MAPPING
==================================================

Inspect how authenticated Replit identity maps to TrailWeigh user records.

Verify:

- Stable provider user ID is used appropriately
- Existing user record is found rather than duplicated
- Email changes do not unnecessarily create a new owner
- Sign-in provider differences do not create duplicate TrailWeigh accounts
  for the same authenticated Replit identity

Do not merge accounts automatically unless the existing architecture already
has a safe verified mechanism.

==================================================
13. AUTHENTICATED REDIRECT
==================================================

After successful sign-in:

The user should return to the intended TrailWeigh experience.

Preserve the existing intended behavior for:

- last active saved file
- restored background
- Locker access
- account-specific state

Do not redirect successful users to a blank/default account if their existing
user record is valid.

Expected:

[ ] Sign-out clears the TrailWeigh auth session appropriately.
[ ] Private Locker data becomes inaccessible while signed out.
[ ] Public/shared links remain available where intended.
[ ] Signing back in restores the correct account.
