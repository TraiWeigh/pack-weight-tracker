6. FIX THE 022R ONE-SHOT SYNC GUARD
==================================================

Inspect:

serverSyncRanRef

or any equivalent one-time guard.

Current 022R logic reportedly does approximately:

if (!userId || serverSyncRanRef.current) return;
serverSyncRanRef.current = true;
fetchLockerEntries()...

This is dangerous because if the first server request fails, the guard can
prevent another synchronization attempt for the remainder of that mounted
session.

Correct this.

Requirements:

- A failed first fetch must NOT permanently disable synchronization.
- The sync guard must be associated with the authenticated user ID, not merely
  one boolean forever.
- Account changes/sign-out/sign-in must not reuse another user's sync state.
- A later successful retry must be possible.
- Avoid infinite fetch loops.

7. ADD SAFE RETRY / REFRESH BEHAVIOR
==================================================

TrailWeigh should retrieve current account Locker data:

- after authentication is ready
- when the private checklist/Locker initializes
- after a failed synchronization when a reasonable retry occurs
- when the page becomes active again after being backgrounded, if appropriate
- when the user returns to TrailWeigh after saving from another device

Do NOT add aggressive polling.

A reasonable model is:
- fetch on authenticated startup
- fetch when page becomes visible/focused again, with debounce/throttle
- fetch after successful local/server mutations as needed

This is especially important on phones, where Safari may keep a page suspended
for a long time.

==================================================
8. FIX THE 022R MIGRATION MERGE FLAW
==================================================

The 022R report says:

IF SERVER HAS ENTRIES:
    replace local Locker with server entries

ELSE:
    migrate local entries to server

This can lose or hide older local-only Locker entries.

Example:

Desktop localStorage contains:
A
B
C

Server contains only:
A

The 022R logic may replace the desktop cache with only A instead of migrating
B and C.

That is NOT safe.

Implement a deterministic merge/migration strategy by STABLE FILE ID.

For authenticated account-owned Locker entries:

SERVER-ONLY ID:
- keep it
- add it to local cache

LOCAL-ONLY ID:
- preserve it
- upload/migrate it to server
- do not discard it just because the server already contains some other files

SAME ID ON BOTH:
- compare valid savedAt/update timestamps where available
- preserve the newest legitimate saved state
- do not generate a new ID
- do not duplicate the file

If timestamps are equal or ambiguous:
- use the safest deterministic rule
- document it

Do not overwrite a newer server version with an older stale local cache.

Do not erase a valid local-only saved file.

==================================================
9. MIGRATION MUST BE CONFIRMED, NOT FIRE-AND-FORGET
==================================================

Existing desktop Locker files are important.

When migrating localStorage entries to the server:

1. Keep the local entries intact.
2. Upload each missing local-only entry.
3. Await/confirm the server result.
4. Re-fetch the server Locker.
5. Confirm all expected stable IDs exist on the server.
6. Only then treat migration as synchronized.

If one item fails:
- preserve it locally
- mark/retry that item
- do not declare the entire Locker synchronized
