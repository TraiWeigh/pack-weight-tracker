============================================================
PURPOSE
============================================================

R0079 implements THREE closely related saved-list workflow changes:

1. Add a DELETE option to an expanded saved-list folder/card in Locker.
2. Change the bottom Save box so it offers:
   - Save
   - Save As
3. Give the existing Reset box a clear purpose:
   RESET CHECKED/PACKED STATE ONLY.

These changes are about saved-list lifecycle and checklist reuse.

R0079 must NOT change Master Library ownership, list-selection logic,
Preview/Print check-state behavior, photo/location architecture, sharing format,
AI list creation, LiDAR ideas, or onboarding.

Those are separate prompts.

============================================================
CURRENT USER REQUIREMENTS
============================================================

A. LOCKER DELETE

When a saved list/folder is expanded in Locker, the user must have a clear Delete option.

Delete means:

- delete THAT SAVED LIST only;
- do NOT delete Master Library items;
- do NOT delete items from other saved lists;
- do NOT alter account/auth;
- do NOT delete photos or other shared assets unless current existing architecture
  clearly treats them as list-owned and safe to remove;
- do NOT change another list currently loaded unless deleting the active list requires
  a safe active-state transition.

Deletion must require confirmation.

B. SAVE BOX

The existing bottom Save box must offer two choices:

- Save
- Save As

SAVE:
- If the currently loaded list already has a persistent saved-list identity:
  update that SAME saved list.
- Do not create a duplicate.
- Preserve the saved list's identity.
- Preserve its current name unless the existing Save flow explicitly includes rename.
- Use the existing persistence architecture.

SAVE AS:
- create a NEW independent saved list/copy;
- ask the user for a new list name;
- do not overwrite the source saved list;
- after successful Save As, the new copy should become the current saved list if that
  is consistent with the existing TrailWeigh save/load model;
- report the exact resulting active-list behavior.

UNSAVED / NEW LIST:
- If no persistent saved-list identity exists yet, choosing Save must use the existing
  naming/save flow to create the first saved list.
- Do not present a meaningless overwrite action when no saved target exists.

C. RESET BOX

The existing Reset control currently does not perform a useful user-visible action.

R0079 defines Reset as:

RESET CHECKED ITEMS / PACKED STATE

When used:
- every currently CHECKED/PACKED item in the active checklist becomes unchecked;
- INCLUDED items remain in the checklist;
- categories remain;
- quantities remain;
- weights remain;
- notes remain;
- photos remain;
- locations remain;
- Master Library membership remains;
- saved-list structure remains;
- nothing is deleted.

Reset must NOT:
- delete items;
- delete categories;
- clear the list;
- reset quantities or weights;
- delete the saved file;
- change Master Library contents;
- remove photos/locations;
- alter item inclusion/selection state.

This establishes a standing product distinction:

INCLUDED IN LIST != CHECKED/PACKED

============================================================
ACTIVE-LIST DELETE EDGE CASE
============================================================

If the saved list being deleted is ALSO the currently active/loaded list:

Do not leave the application pointing at a deleted persistent identity.

Determine the existing application's safest current behavior.

Preferred outcome:
- delete the saved Locker copy;
- keep the currently visible working list in memory as an UNSAVED working list,
  with its data intact;
- next Save creates a new saved list rather than silently recreating the deleted ID.

If current architecture cannot safely do that without broad work:
- use the least-destructive existing behavior;
- explain the behavior clearly in the report;
- do not silently wipe the visible active list.
