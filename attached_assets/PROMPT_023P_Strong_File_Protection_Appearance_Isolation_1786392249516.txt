PROMPT 023P — STRONG FILE PROTECTION: ISOLATE ALL EDIT VIEW APPEARANCE SETTINGS PER SAVED FILE

PURPOSE

A serious file-protection problem has been found.

The user verified that changing these Edit View settings in one file can affect other previously saved Locker files when those files are opened:

- Transparency
- Bar Color
- Font

Assume Text Color and other file-specific Edit View appearance settings may be vulnerable until proven otherwise.

This is NOT acceptable.

A saved TrailWeigh file must preserve its own appearance state. Changing one working file must never silently alter another saved file.

PROMPT 023O must now be treated as PARTIAL because the appearance feature works visually but violates saved-file isolation.

This prompt has priority over the planned eyedropper work.

DO NOT work on eyedropper safety in this prompt.
DO NOT redesign Edit View.
DO NOT perform unrelated refactors.

==================================================
0. CHECKPOINT / DATA PROTECTION — REQUIRED FIRST
==================================================

Before editing:

1. Create a checkpoint.
2. Inspect the current saved-file schema/data model and appearance-state architecture.
3. Identify where each Edit View setting currently lives:
   - React/component state
   - context
   - localStorage
   - sessionStorage
   - Locker saved-file payload
   - user/account preference storage
   - BroadcastChannel/storage events
   - backend/database
4. Identify whether current saved files are:
   A. actually being rewritten/modified, or
   B. merely rendered with leaked/global appearance values.
5. DO NOT bulk rewrite existing saved files.
6. DO NOT run a destructive migration.
7. DO NOT overwrite Locker contents during diagnosis.
8. Preserve existing file IDs, names, checklist data, categories, quantities, weights, checked states, backgrounds, and user ownership.
9. Inspect the complete final diff and revert unrelated changes.
10. Document the checkpoint, diagnosis, and final diff.

==================================================
1. FILE IS THE PROTECTION BOUNDARY
==================================================

Treat each TrailWeigh saved file as an independent document.

A saved file's appearance may change only when:

1. that specific file is opened as the active working file,
2. the user changes its appearance,
3. the user explicitly saves that file.

Changing File A must NOT alter File B.

Opening File B must NOT import File A's current/live appearance.

This rule applies even when both files belong to the same signed-in account.

==================================================
2. PROTECT ALL FILE-SPECIFIC EDIT VIEW SETTINGS
==================================================

Inventory every current setting inside Edit View.

At minimum protect:

- selected background/theme
- Full Screen / Fit Image or equivalent fit/fill state
- Light/Dark appearance state if currently stored per file
- Darken
- Transparency
- Bar Color
- Text Color
- Font

Also inspect any other current Edit View setting not listed above.

For every appearance setting that is intended to belong to a saved list/document:

- store it in that file's saved appearance state
- load it from that file when opened
- keep unsaved edits isolated to the active working file
- save it only into the active file when the user explicitly saves

Do not accidentally convert true account-wide accessibility/preferences into file-specific state. If any current setting is genuinely global by design, document it and leave it global.

==================================================
3. REMOVE GLOBAL APPEARANCE LEAKAGE
==================================================

Find and eliminate any path where file-specific appearance settings are being treated as global/shared live preferences.

Inspect especially:

- localStorage keys shared across files
- account-level appearance objects
- storage-event listeners
- BroadcastChannel messages
- shared React context initialized from "last used" values
- effects that write appearance changes immediately
- effects that apply one file's appearance to all tabs/windows
- fallback logic that uses the last active file's appearance
- Save/Load code that merges global appearance into opened files

Do not simply hide the symptom.

Fix the ownership model so file-specific appearance belongs to the active file/document.

==================================================
4. UNSAVED EDITS MUST STAY WITH THE CURRENT WORKING FILE
==================================================

When File A is open:

- changing Bar Color should change File A's current working view only
- changing Font should change File A's current working view only
- changing Transparency should change File A's current working view only
- changing any other file-specific Edit View setting should remain local to File A

Until File A is explicitly saved:

- File A's persisted saved version must remain unchanged
- File B must remain unchanged
- other open files/tabs must remain unchanged

==================================================
5. SAVE BEHAVIOR
==================================================

SAVE EXISTING FILE

If File A is active and the user clicks Save:

- write File A's current checklist/content state
- write File A's current file-specific appearance state
- update File A by its existing file ID
- do not modify any other file

SAVE AS

If File A is active and the user chooses Save As:

- create a NEW file ID
- copy the current working checklist/content
- copy the current working appearance state
- preserve the original File A unchanged

This must behave like a true document copy.

==================================================
6. OPEN / LOAD BEHAVIOR
==================================================

When File B is opened from Locker:

- load File B's own saved appearance
- do not merge in File A's current appearance
- do not use "last used" Bar Color, Font, Transparency, etc.
- do not overwrite File B during open

Opening a file is READ/LOAD behavior, not SAVE behavior.

==================================================
7. NEW FILE BEHAVIOR
==================================================

A brand-new unsaved file must start with TrailWeigh's intended default appearance.

It must NOT inherit live appearance changes from the currently open file.

For example:

File A:
- red Bar Color
- Georgia font
- 40% Transparency

Click New.

New unsaved file should use TrailWeigh defaults, not:
- red
- Georgia
- 40%

Do not change established New-list content behavior.

==================================================
8. EXISTING SAVED FILES THAT LACK NEW APPEARANCE FIELDS
==================================================

If older Locker files do not contain some newer appearance fields:

- do NOT pull values from the last-used/global appearance state
- use stable TrailWeigh defaults for missing fields
- preserve all existing file content
- do not rewrite the file merely because it was opened

If a safe schema-version or defaulting strategy is needed, implement the smallest backward-compatible solution.

Document it.

==================================================
9. DO NOT SILENTLY MODIFY SAVED FILES ON OPEN
==================================================

This is critical.

Opening/loading File B must not update its `updatedAt`, contents, appearance, or persisted record unless the user explicitly saves.

Verify this with backend/storage inspection.

If the current code auto-persists appearance during load/render, stop that behavior for file-specific appearance state.

==================================================
13. UNDO / REDO
==================================================

Undo/Redo for appearance changes must operate only within the current working file/session.

Undo in File A must not affect File B.

If the user switches files, do not apply A's appearance-history entries to B.

Preserve current established Undo/Redo behavior otherwise.

==================================================
14. RESET BAR/TEXT
==================================================

Reset Bar/Text must affect only the active working file.

It must not reset any other saved file.

If the active file is not saved afterward, other persisted records remain untouched.
