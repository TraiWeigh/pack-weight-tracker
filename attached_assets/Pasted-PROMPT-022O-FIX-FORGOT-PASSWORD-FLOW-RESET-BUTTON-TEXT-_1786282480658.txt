PROMPT 022O — FIX FORGOT PASSWORD FLOW + RESET BUTTON TEXT CONTRAST

GOAL

Fix two issues on the TrailWeigh authentication recovery screen:

1. The green "Reset your password" button currently uses text that is too dark.
   The button label must be WHITE.

2. The Forgot Password / password recovery flow is not working correctly.
   The user reports that password recovery is failing, and there are only
   2 remaining attempts left.

This prompt is both a visual fix and an authentication-recovery diagnosis/fix.

IMPORTANT

Because the user has only 2 attempts left, do NOT continue blind manual
password-attempt testing in a way that could lock the account.

Use safe testing methods and inspect the logic carefully.

==================================================

Before making any changes:

1. Create the normal Replit checkpoint/backup.

2. Inspect the current authentication architecture.

3. Identify the code/components used for:
   - Forgot Password screen
   - Reset your password button
   - Password-based sign-in
   - Password reset flow
   - Rate-limit / attempt-limit messaging
   - Alternative sign-in methods:
     - Continue with Google
     - Email code
   - Error handling and user feedback

4. Make the smallest reasonable change.

5. Do NOT redesign the auth pages.

6. Do NOT make risky test attempts on the real user account.

7. If a test account or safe dev account can be used, use that instead.

==================================================

On the Forgot Password screen:

The green primary button labeled:

Reset your password

must use:

- WHITE text
- white or very light icon text if an icon exists

Preserve the existing green button style, but fix the text contrast so the

GREEN BUTTON
+ WHITE LABEL TEXT

==================================================
2. DIAGNOSE THE PASSWORD RECOVERY FAILURE
==================================================

The user reports:

- Password still is not working
- They only have 2 more attempts left
- They are using the Forgot Password / recovery flow

You must determine exactly what is failing.

Investigate whether the issue is caused by:

A. Wrong password verification logic
B. Broken password-reset token/email flow
C. Password reset not actually saving the new password
D. UI showing "reset" but backend not completing the reset
E. Session/state confusion after reset
F. Account method mismatch
   (example: account was created with Google sign-in, not password sign-in)
G. Attempt counter / throttling logic behaving incorrectly
H. The "Email code" and/or "Continue with Google" path not being explained
   clearly enough to the user

Do not guess. Inspect the real logic.

==================================================
3. IMPORTANT ACCOUNT-METHOD CHECK
==================================================

Specifically verify whether the affected account may actually be tied to:

- Google sign-in
- passwordless email sign-in
- password sign-in
- multiple auth providers

If the account was originally created with Google, the UI must not mislead
the user into thinking a normal password reset is the correct method.

If necessary, improve the user-facing message so it is clear which recovery
method should be used.

==================================================
4. ATTEMPT COUNTER / WARNING MESSAGE
==================================================

Inspect the warning message:

"There are only 2 remaining attempts."

Verify:

- What triggers the count
- Whether attempts are being consumed correctly
- Whether opening the flow or changing method consumes attempts
- Whether only actual failed password attempts decrement the counter
- Whether reset attempts are incorrectly consuming sign-in attempts
- Whether the warning is shown in the right context

If the logic is wrong, fix it.

A password reset flow should not behave in a way that unnecessarily burns the
user's remaining sign-in attempts.

==================================================
5. USER FEEDBACK / ERROR MESSAGING
==================================================

If password reset fails, the user must receive a clear message.

Bad example:
- Generic silent failure
- Vague "something went wrong"
- No clue what to do next

Better examples:
- "This account uses Google sign-in. Please choose Continue with Google."
- "We sent a reset link/code to your email."
- "Your password was updated successfully. Please sign in with your new password."
- "Too many failed password attempts. Use email code or wait until retry is allowed."

Make messages specific and helpful.

Do NOT expose sensitive backend information.

==================================================
6. SUCCESS PATHS MUST BE CLEAR
==================================================

If a user successfully resets their password:

- Make it obvious that the reset succeeded
- Tell them what to do next
- Route them correctly back to sign-in if needed
- Ensure the new password actually works

If the correct action is to use Google sign-in or email code instead,
make that obvious.

- Get help

toward the correct option.
