# PART 3 — DO NOT STORE FULL PHOTO DATA IN LOCALSTORAGE

Do not continue storing full-resolution images, Base64 image strings, blobs converted to text, or large data URLs directly in localStorage.

Use localStorage only for small metadata when appropriate, such as:

- Theme IDs
- Theme names
- Photo IDs
- Photo order
- Selected theme ID
- Selected photo ID
- Fill/Fit setting
- Light/Dark setting
- Fade/darken setting
- Migration version

Store uploaded photo binary data in IndexedDB.

Preferred structure:

## IndexedDB database

Use one clearly named TrailWeigh database or extend an existing suitable database.

Create an image store containing records such as:

- `photoId`
- `blob`
- `mimeType`
- `width`
- `height`
- `createdAt`, only if useful

## Theme metadata

Theme records should reference photo IDs rather than containing full image data.

Example concept:

- Theme ID
- Theme name
- Ordered array of photo IDs

## Active background

Store only a stable reference such as:

- Built-in background identifier or URL
- Custom `photoId`

Do not copy the full custom image into the active-background record.

Do not duplicate the same image data when:

- It is uploaded
- It is selected
- The checklist is saved
- Save As is used
- New is used
- A Locker file is opened
- Undo or Redo is used

# PART 4 — RESIZE AND COMPRESS UPLOADED PHOTOS

Before saving a user-uploaded photo, create a background-sized optimized version.

Do not permanently store the original full-resolution image unless the existing application has a documented reason.

Requirements:

- Preserve aspect ratio.
- Do not stretch or distort the image.
- Preserve enough resolution for a desktop background.
- Reduce extremely large phone or camera photos before saving.
- Preserve orientation correctly.
- Handle JPEG, PNG, WebP, and other formats already supported by TrailWeigh.
- Preserve transparency where practical for formats that require it.
- Do not unnecessarily convert a transparent PNG into a black background.

Use a reasonable maximum long-edge dimension, such as approximately 1920–2048 pixels, unless current application measurements justify another value.

Use a sensible compressed format and quality.

Document in the report:

- Maximum dimensions
- Output format
- Compression quality
- Typical before-and-after file sizes
- How PNG transparency is handled
- What happens when image decoding fails

Do not make thumbnails so low-quality that they look blurred as the checklist background.

# PART 5 — SAVE FIRST, THEN SHOW SUCCESS

The current interface can show a photo as added even when browser storage later fails.

Correct the sequence.

When a photo is uploaded or dropped:

1. Validate the file.
2. Decode the image.
3. Resize/compress it.
4. Save the optimized blob to IndexedDB.
5. Save or update theme metadata.
6. Confirm both storage operations succeeded.
7. Only then show the photo as successfully added and increase the counter.

Do not display a permanent photo thumbnail or increase `0/10` to `1/10` until persistence succeeds.

A temporary loading state is allowed.

Example loading text:

`Saving photo…`

After success:

- Display the thumbnail.
- Increase the count.
- Keep the Background Edit panel open.
- Make the photo available for selection.

# PART 6 — HANDLE STORAGE FAILURES SAFELY

Catch all relevant IndexedDB, image-processing, and browser-storage errors.

Never allow a normal storage failure to reach:

- The Vite error screen
- An uncaught runtime overlay
- A blank application
- A browser navigation error

If a photo cannot be saved:

- Remove any partial image record.
- Roll back incomplete theme metadata.
- Keep the original Add Photo position available.
- Do not increase the photo count.
- Show a clear TrailWeigh message.

Suggested message:

`This photo could not be saved. Try a smaller image or remove unused theme photos.`

When the cause is specifically storage capacity, a message may say:

`Photo storage is full. Remove unused theme photos before adding another.`

Do not expose technical stack traces to the user.

Log enough technical detail for development without displaying it in the user interface.

- Replace old image data in theme metadata with stable photo IDs.

- Do not crash the app.
- Record the failure honestly in the report.

# PART 10 — PHOTO REMOVAL AND THEME DELETION

- Remove its ID from its theme.
- Delete its IndexedDB blob when no remaining valid reference uses it.
- Replace its position with Add Photo.
- Update the count.
- Preserve all other photos.

If it is the active background:

- Select another photo in the theme when appropriate.
- Otherwise fall back to Landscapes.
- Do not retain a large stale image string.

- Remove the theme metadata.
- Delete its IndexedDB photo blobs when they are not referenced elsewhere.
- Remove the theme from the dropdown.
- Switch to Landscapes when the deleted theme was selected.
- Make Add Theme available again if fewer than ten custom themes remain.

The built-in Landscapes theme must never be deleted.
