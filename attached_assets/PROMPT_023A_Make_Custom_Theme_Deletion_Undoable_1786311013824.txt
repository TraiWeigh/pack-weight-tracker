The deleted custom theme DID NOT come back.

The user expects custom-theme deletion to participate in TrailWeigh's existing

Do NOT redesign Background Themes.
Do NOT change unrelated mobile layout work.
Do NOT change Locker synchronization.

==================================================
1. REQUIRED USER BEHAVIOR
==================================================

Correct sequence:

1. User opens Background Edit.
2. User clicks the trash icon for a custom theme.
3. User confirms "Delete Theme" once.
4. Theme disappears.
5. User clicks TrailWeigh's existing global Undo button ONCE.

Expected:

- Deleted custom theme returns.
- Same theme name returns.
- Same theme ID returns where architecture allows and is safest.
- Same custom photos return.
- Same photo order returns.
- Same photo count returns.
- Same Fit / Fill behavior remains.
- If that deleted theme had been active before deletion, Undo restores the
  prior active-theme/background state.
- No duplicate theme is created.

Then:

6. User clicks Redo ONCE.

Expected:

- The same custom theme is deleted again.
- No duplicate delete occurs.
- No broken photo references.
- No second confirmation dialog is required for Redo.

==================================================
2. USE THE EXISTING GLOBAL UNDO / REDO SYSTEM
==================================================

Do NOT build a separate custom-theme-only Undo button.

Integrate the deletion action into TrailWeigh's EXISTING global Undo / Redo
history.

Inspect the current history entry structure and extend it only as much as
needed.

Earlier TrailWeigh background work already uses history snapshots for
background changes.

Prefer extending that architecture rather than creating a second independent
history stack.

==================================================
3. SNAPSHOT BEFORE DELETION
==================================================

Immediately BEFORE a confirmed custom-theme deletion:

Capture a complete undo snapshot sufficient to restore the theme.

The snapshot must include all data needed to reconstruct the custom theme,
including where applicable:

- theme stable ID
- theme name
- theme ordering/index
- photo IDs
- photo metadata
- photo order
- photo storage references
- actual image/blob records if references would otherwise be destroyed
- Fit / Fill state if theme-specific
- currently selected/active theme
- currently displayed photo/background
- account/device sync metadata needed to restore safely

Do not assume theme metadata alone is enough if deleteTheme also destroys photo
records.

==================================================
4. DO NOT DESTROY THE ONLY COPY NEEDED FOR UNDO
==================================================

The current delete path may physically remove custom photo records/assets.

If those assets are permanently destroyed immediately, Undo cannot restore the
theme.

Change the deletion lifecycle safely.

Acceptable approaches include:

A. Store a complete restorable snapshot in the existing history entry before
   deletion.

OR

B. Move deleted theme/photo data into a temporary undo cache/tombstone until
   the history entry is no longer recoverable.

OR

C. Use another existing reversible data mechanism already present in the app.

Choose the smallest safe solution that fits the existing architecture.

DO NOT:
- permanently delete the only copy and then pretend Undo can restore it
- recreate empty photo placeholders
- restore only the theme name without the images
- generate new unrelated photo IDs unless absolutely required

==================================================
5. PRESERVE STABLE IDS
==================================================

Undo should restore the original custom-theme identity wherever safely
possible.

Preferred:

Theme ID before delete:
abc123

Undo:
abc123 returns

Redo:
abc123 is deleted again

This avoids:
- duplicate themes
- broken references
- saved-list/background reference mismatch
- share/background mismatch

If the current storage architecture makes exact ID restoration impossible,
document why and preserve all higher-level references safely.

==================================================

==================================================

Test when the deleted custom theme is currently active.

That fallback is correct during the deleted state.

But if the user presses Undo:

Expected:

- custom theme returns
- its photos return
- the prior active custom theme becomes active again
- the previously displayed custom background is restored where possible
- no broken image
- no missing theme ID
- no fallback theme remains selected incorrectly

- no history corruption

Then click Undo again.

Expected:

- theme restores again

Test at least:
DELETE → UNDO → REDO → UNDO
