## Lessons for Future Prompts

### Learning Question 1
**What source pattern allowed obsolete stacked-bar gesture machinery to remain after the user-visible lift path was disabled, and what future prompt rule would better ensure obsolete interaction code is actually removed rather than merely made unreachable?**

R0073 disabled the lift path by changing `d.mode` to always be `'scroll'` — but it left the `lift` state, `settling` state, `'lift'` in the type union, the `else if (d.mode === 'lift')` branch, and the `translateY(${-lift}px)` transform all intact. Because the mode could never reach `'lift'`, none of these code paths could fire at runtime. TypeScript did not flag any of them as errors (the type union still declared `'lift'` as a valid member, so the branch was not a type error — just an unreachable execution path).

**Rule:** When a gesture mode or interaction path is disabled by changing a mode-lock condition, the disabling PR/task must explicitly list every downstream consumer of that mode (state variables read when mode equals X, style expressions computed from that state, event handlers that call `setState` for that state) and remove them in the same change. "Making a path unreachable" is not the same as "removing the path." Future prompts that disable a gesture mode should end with: *"After disabling, grep for all references to the old mode name and the state it wrote — remove every one, then run typecheck."*

### Learning Question 2
**Why did the earlier Playwright category test pass without actually proving the category was open, and what assertion pattern should future TrailWeigh tests use to prove required UI preconditions before testing the final condition?**

The R0073 CA01 test did `catBar.click()` and then immediately checked for `"Add item to …"` buttons. This passed (0 buttons found) because the button was removed from the source — but the category was not visibly open in the screenshot. The test's precondition — "category is open" — was never asserted. Playwright does not fail on missing preconditions; it only fails on explicit `expect()` calls. A test that checks a condition without first verifying the required context is structurally incomplete even when it returns 0 failures.

**Pattern for future TrailWeigh tests:** Every test of a UI state that depends on a prior interaction must include a *precondition proof* assertion before the final assertion. For accordion open/close: (1) assert `aria-expanded === 'true'` on the toggle button, and (2) assert a known child element is visible. Both must pass before the target condition (absence of "+ Add Item") is tested. This two-step pattern ensures the screenshot and the log are meaningful and that a green result genuinely proves the requirement.

### Learning Question 3
**What should future TrailWeigh reports do when a required runtime precondition—such as a genuinely overflowing deck—cannot be created, so that NOT RUN is not incorrectly presented as PASS?**

R0073's TO05 returned early (via `return`) in a Playwright `test()` body after logging "SKIP." Playwright still counted the test as PASS (0 failures in the run) because no `expect()` failed. The report then described the deck behavior as "confirmed in that state" — which was a non-overflowing state, not the overflowing state the test was designed to prove.

**Rule:** When a precondition cannot be satisfied:
1. The test body must log `NOT RUN` with a clear reason, and call `test.skip()` or simply return early with the console message.
2. The report must list this item under a separate *NOT RUN* column — never under *PASS*.
3. The Playwright run summary ("N passed") must be accompanied by a product-requirement table that explicitly calls out NOT RUN items, because a zero-failure run does not mean every product requirement is verified.
4. If possible, include measurements (e.g. clientH and scrollH for each deck) to document *why* the precondition could not be met, so a future reviewer can identify the conditions under which the test should run.
