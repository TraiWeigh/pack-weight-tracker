## Root Cause

The prior R0076 implementation applied `maxHeight + overflowY: auto` to the item-row container, which correctly bounded the item rows' own scroll. However, the parent `main-scroll` div (which contains all category cards in normal flow) remained **scrollable**. This meant:

1. **Category header was not stationary.** A finger-scroll within the item viewport could propagate to `main-scroll` when the item container reached its scroll limit, carrying the category header upward out of view.
2. **Add Item bar was not stationary.** It lived in normal flow inside the category card, so `main-scroll` scrolling could carry it below or behind the nav bar.
3. **Only one toggling chevron existed**, not two separate ▲/▼ controls with independent disabled states.
4. **Re-detection on item add/delete was absent.** SHORT→LONG transitions required close + reopen.
5. **Measurement error.** `remeasureLongMode` computed `rawAvailH = navTop − summaryBtm − CARD_H − 44`. Sub-pixel differences between `summaryBottom` and the actual item container top caused a 4px overshoot of `addItemBottom` past `bottomControlsTop`.

## Final Layout Architecture

```
main-scroll  (overflowY: hidden when isCatLong && !allExpanded)
  └── list-summary-bar  (position: sticky, top: 0, zIndex: 4)
  └── catListRef  (normal flow)
       └── [data-cat="Backpack"]  (category card)
            ├── cat-header-open   (68px, data-testid when open single-open mode)
            │    └── wedge button + name/weight grid
            ├── open-cat-items    (maxHeight: availItemH, overflowY: auto when isCatLong)
            │    └── item rows (44px each, scroll independently)
            └── cat-add-item-bar  (44px, always outside item container)
                 ├── Add Item button
                 └── [cat-chevron-up] + [cat-chevron-down]  (isCatLong only)
```

**Key design decisions:**
- `main-scroll` is locked to `overflowY: hidden` while a long category is open. The category card was already positioned by the open-cat RAF scroll. Freezing the parent prevents any further movement.
- `remeasureLongMode()` measures from `itemsEl.getBoundingClientRect().top` (= actual headerBottom at layout time), not from `summaryBtm − CARD_H`. This eliminates the 4px overshoot.
- Short/long detection fires both on category open (420ms RAF) and on `openCatItemCount` change (150ms delay), enabling seamless SHORT→LONG and LONG→SHORT transitions.
- Two separate ▲/▼ buttons replace the single toggling chevron. Both always present in long mode; `disabled` + `aria-disabled` set programmatically.
- Auto-scroll to bottom of item viewport fires when `openCatItemCount` increases while in long mode.

**Short vs long detection:**
```ts
rawAvailH = navTop − itemsEl.getBoundingClientRect().top − 44
isCatLong = itemsEl.scrollHeight > rawAvailH + 4
```

**Expand All:** `allExpanded` remains the all-categories-open flag. Long-mode bounds (`isCatLong && !allExpanded`) are inactive when all categories are expanded — normal parent scrolling continues.

## Lessons for Future Prompts

### Learning Question 1
*What exact parent/child layout structure lets the category header and Add Item bar remain stationary while only the item rows scroll?*

**Answer:** The category card remains in `main-scroll`'s normal flow. The key is to **freeze `main-scroll`** (`overflowY: hidden`) once a category enters long mode. The category header and Add Item bar are already positioned at the right location (via the initial scroll-into-view RAF). Freezing the parent makes both elements truly stationary — no `position: fixed` required. Only the item container, which has its own `overflowY: auto + maxHeight`, continues to scroll independently.

### Learning Question 2
*Which state/measurement should determine when a category switches from normal-flow to bounded long-category mode?*

**Answer:** Compute `rawAvailH = navTop − itemsEl.getBoundingClientRect().top − 44` using **live DOM positions** from the item container's own top (= headerBottom at layout time). Set `isCatLong = itemsEl.scrollHeight > rawAvailH + 4`. Re-run this measurement both on category open (420ms after RAF scroll) and on `openCatItemCount` change (150ms delay) to handle SHORT→LONG transitions without close/reopen. Never use stale React state (`summaryH`, `navHeight`) for these critical pixel calculations.

### Learning Question 3
*What Playwright geometry checks best prove the header and Add Item bar are stationary while the item viewport scrolls?*

**Answer:** (1) Record `headerTop/headerBottom/addItemTop/addItemBottom` before and after scrolling the item container (via `el.scrollTop += N` in `evaluate`, not mouse drag — mouse drag does not reliably produce scroll events in an `overflowY: auto` div). Assert `|before − after| ≤ 1px` for all four values. (2) Verify `itemViewportScrollTop` changed. For ▲/▼ states: set `el.scrollTop = 0 / mid / max` via `evaluate` and read `getAttribute('disabled')` + `getAttribute('aria-disabled')` directly — do not rely on UI-driven scroll for state setup in timing-sensitive tests.

## Remaining Defects / Uncertainty

1. **2px header sub-pixel offset** — `headerTop` lands 2px above `summaryBottom` due to smooth-scroll + `getBoundingClientRect()` floating-point rounding. Visually unnoticeable (only top 2px of background affected; all header content visible). Test tolerance set to 3px.
2. **F01 dHdr=1.00px** — On each item add in long mode, the header drifts exactly 1px during the re-measure effect. This is within the 1px test tolerance. Likely caused by fractional CSS pixel rounding during `maxHeight` re-application.
3. **G01 NOT RUN** — LONG→SHORT transition via delete is architecturally equivalent to SHORT→LONG (same re-measure effect triggered by `openCatItemCount` decrease) but is not tested end-to-end due to slide-to-delete gesture complexity.
