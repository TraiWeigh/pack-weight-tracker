## M. UNIQUE FINDINGS BY SEVERITY

### FINDING 1 — Focus indicator reliance on CSS-only mechanisms (MODERATE)

**WCAG rule:** 2.4.7 Focus Visible (AA), 2.4.11 Focus Appearance (AA, WCAG 2.2)  
**Severity:** MODERATE  
**Nature:** NEEDS MANUAL VERIFICATION  

**Description:**  
The structural scan detects 38–93 focusable elements per UI state with `outline: none` or
`outline-width: 0px` at computed style (default/non-focused state). This is expected: the app
applies `:focus-visible` CSS classes and `box-shadow`-based indicators for many controls.

R0077P2 added explicit `outlineWidth: 2px` (weight input) and `3px` (delete button) focus
outlines. The nav buttons and category wedge buttons likely use custom indicator patterns.

**Why this needs manual verification:**  
The structural scan reads computed outline in the default (non-focused) state.  
`outline: none` in default state is NOT a WCAG violation if `:focus-visible` applies a visible
indicator when the element is focused. Automated tools cannot read `:focus-visible` state
without injecting focus — that requires either axe-core or keyboard navigation observation.

**Affected controls / count:**  
All interactive elements — nav buttons, category wedges, item rows, checkboxes, inputs, selects.  
Count: 38 (collapsed list) to 93 (long-category mode with many item rows).

**Root cause (likely):** Global `border: none; outline: none` on button elements, with custom
focus indication via `:focus-visible` CSS and/or React inline styles applied on focus event.

**Recommended repair concept:**  
Manual keyboard walkthrough across all 10 states, observing visible focus indicators.  
If any focusable element has no visible indicator during `:focus-visible`, add one.  
Safe to repair in the web app without breaking other behavior.

---

### FINDING 2 — Category drag-to-reorder handle has no accessible name or keyboard role (SERIOUS)

**WCAG rules:** 1.3.1 Info and Relationships, 2.1.1 Keyboard, 4.1.2 Name, Role, Value  
**Severity:** SERIOUS  
**Nature:** REAL PRODUCT ISSUE  

**Description:**  
The category drag-to-reorder handles render as visual icons without a `<button>` role or
`aria-label`. The test `'Drag-to-reorder handle has aria-label and title'` looks for
`getByRole('button', { name: /Drag to reorder Backpack category/i })` and finds 0 elements.

A grep of `MobileFunctionalV3.tsx` confirms: no `aria-label` containing "drag" or "reorder"
is applied to any drag handle element. The handle is likely a styled `<div>` with pointer
events for drag-to-reorder but no accessible name or keyboard trigger.

**Affected controls:** All category reorder handles (6 categories in demo list).  
**Count:** 6 instances.

**Recommended repair concept:**  
Add `role="button"`, `aria-label="Drag to reorder [CategoryName] category"`,
`title="Drag to reorder [CategoryName] category"`, and a `tabIndex={0}` + keyboard handler
so the control is reachable and operable without a mouse.

**Repair feasibility:** Safe to implement in the current web app. **Do NOT repair in R0078.**
