## Findings & Fixes

### FINDING 1 — Delete Item button had `padding:0`, effective height ~20px (P2-01)

**Problem:** The expanded-item Delete row set `alignItems:'flex-start'`, so the
button inside it did not stretch to fill the row's `minHeight:44`.

**Fix (`MobileFunctionalV3.tsx`):**
- Delete row: `alignItems:'flex-start'` → `alignItems:'stretch'`
- Delete button: added `minHeight:44, display:'flex', alignItems:'center'`
- Added `data-testid="expanded-item-delete-btn"` for stable test addressing

**Test result (P2-01):** PASS — Delete btn box = 338.0×44.0

---

### FINDING 2 — Weight/Qty/Move rows had `height:42`, inputs not guaranteed ≥44px (P2-02/P2-03/P2-04)

**Problem:** The three editable rows used `height:42` (a hard height) and the inner
`<input>` / `<select>` controls had no explicit height, leaving them ~20px tall.

**Fix (`MobileFunctionalV3.tsx`):**
- Weight row: `height:42` → `minHeight:44`; weight `<input>`: `minHeight:44` + `data-testid="expanded-weight-input"`
- Qty row: `height:42` → `minHeight:44`; qty `<select>`: `minHeight:44` + `data-testid="expanded-qty-select"`
- Move row: `height:42` → `minHeight:44`; move `<select>`: `minHeight:44` + `data-testid="expanded-move-select"`

**Test results:**
- P2-02 PASS — Weight input box = 72.0×44.0; value committed on blur
- P2-03 PASS — Qty select box = 55.0×44.0; selection updates (1→2)
- P2-04 PASS — Move select box = 109.0×44.0; item moved successfully

### FINDING 3 — R0077 keyboard test used `.focus()` not natural Tab (P2-05)

**Problem:** R0077 A05 focused elements directly via `.focus()`, which does not
prove natural keyboard reachability.

**Fix (test only):** P2-05 starts from the item checkbox (first focusable element
in the row), then uses real `page.keyboard.press('Tab')` events and verifies that
at least one of the three expanded controls (`expanded-weight-input`,
`expanded-qty-select`, `expanded-item-delete-btn`) is reached within 12 Tab presses.

**Test result (P2-05):** PASS — Natural Tab reached: weight-input at Tab 2,
qty-select at Tab 3, delete-btn at Tab 5.
```
Tab sequence: INPUT[expanded-weight-input] → SELECT[expanded-qty-select] →
SELECT[expanded-move-select] → BUTTON[expanded-item-delete-btn] → …
```

---

### FINDING 4 — Delete dialog had no initial focus, Escape, Tab containment, or focus return (P2-07/P2-08/P2-09/P2-10)

**Problem:** The delete confirmation dialog opened without managing keyboard focus,
allowing Tab to escape the modal and leaving the user disoriented after dismissal.

**Fix (`MobileFunctionalV3.tsx`):**
- Added refs: `deleteTriggerRef`, `cancelDialogBtnRef`, `confirmDialogBtnRef`
- On dialog open: `setTimeout(50)` shifts focus to Cancel button (safe default)
- Cancel button click: sets `deleteConfirmedRef=false`, returns focus to `deleteTriggerRef`
- Delete button click: sets `deleteConfirmedRef=true`, focus moves to `cat-add-item-btn`
- `onKeyDown`: Escape closes dialog + restores trigger focus; Tab wraps between
  the two buttons only (focus trap)
- Backdrop click: treated as Cancel

**Test results:**
- P2-07 PASS — Dialog initial focus → `BUTTON[aria-label="Cancel delete item"]`
- P2-08 PASS — Tab: Cancel→Confirm, Tab again wraps back to Cancel; Shift+Tab: Cancel→Confirm
- P2-09 PASS — Escape closes dialog; 0 items deleted; focus returned to `expanded-item-delete-btn`
- P2-10 PASS — Keyboard Tab+Enter confirms delete; item removed; focus on `cat-add-item-btn`

### FINDING 5 — 200% zoom and text-enlargement had never been tested (P2-11/P2-12/P2-13)

**Problem:** R0077 A11 labelled a viewport-width reduction as "150% zoom" but the
relationship was loose. 200% was not tested. Text-size enlargement (root font-size
override) was absent.

**Fix (tests):**  
Three honest tests added with documented methodology and limitations:

- **P2-11** — Viewport 260×563 (390÷1.5 × 844÷1.5), labelled BROWSER-ZOOM EQUIVALENT.  
  Verifies: category open, item expand, weight/qty/delete controls visible, no horizontal overflow.

- **P2-12** — Viewport 195×422 (390÷2 × 844÷2), labelled BROWSER-ZOOM EQUIVALENT.  
  Verifies: app renders without JS crash; categories accessible; delete control visible.

- **P2-13** — Injects `document.documentElement.style.fontSize='200%'` at base 390×844 viewport.  
  Documents the honest limitation: TrailWeigh uses absolute `px` sizes for most
  typography; this test only exercises `rem`/`em`-based controls. Native iOS
  Dynamic Type is NOT claimed.

**Test results:**
- P2-11 PASS — 150% equiv (260×563): core tasks usable, no horizontal overflow
- P2-12 PASS — 200% equiv (195×422): app renders without crash; delete btn visible=true
- P2-13 PASS — root font-size=32px after injection; no horizontal overflow; no page errors

## Technical Notes

### Why `gotoDemo()` was not used in P2 tests
`gotoDemo()` in `tests/e2e/helpers/trailweigh.ts` waits for `getByText('LIST SUMMARY')`,
a string that was replaced by the active list name in a prior revision. The P2 spec uses
the same `beforeEach` pattern as R0077: navigate to `BASE` and wait for
`[data-testid="main-scroll"]`, which is the stable V3 readiness signal.

### Long-mode activation for P2-14 and P2-16
`isCatLong` is computed by `remeasureLongMode()` which fires: (a) when the category
opens, and (b) 150ms after each item-count change (repair effect). At the 390×844
viewport, the threshold requires >14 items to guarantee activation. Tests add 15 items
(3→18) and wait 500ms for the repair to complete before performing the scroll/reveal
assertions.

### Nav carousel — Group 4 navigation (P2-17)
The bottom nav starts on Group 1 (Locker|Summary|Add|Search). Save/Share/More live
in Group 4. P2-17 clicks "Next controls" three times (one per group) to reach Group 4,
then asserts the Save button is visible within `[data-group-idx="3"]`.
