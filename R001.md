## D. GESTURE-INTENT ARBITRATION DESIGN

The following state machine describes the smallest robust design compatible with the existing architecture. It does not propose arbitrary threshold values; all are either derived from the existing code or from established platform guidance.

### D1. State machine

```
IDLE → [pointerdown in gesture zone, not protected] → PENDING
PENDING → [movement > INTENT_PX, |dx| > |dy|] → HORIZONTAL_L or HORIZONTAL_R
PENDING → [movement > INTENT_PX, |dy| > |dx|] → SCROLL (immediately release capture)
PENDING → [pointerup, |displacement| < TAP_PX] → TAP (fire deferred category action if any)
HORIZONTAL_L/R → [pointerup / pointercancel] → IDLE (snap to open or closed)
SCROLL → [pointerup / pointercancel] → IDLE
TAP → IDLE
```

### D2. State descriptions

**1. Touch/pointer start (`IDLE → PENDING`):**
- On `pointerdown` anywhere in the left or right gesture zone (defined as the outermost `GESTURE_W` px of the phone frame)
- Record `{ startX, startY, startTime, ownerSide: 'left'|'right', pendingTarget: element }` in a ref
- Do NOT call `setPointerCapture` yet
- If pointer starts outside gesture zones → pass through, stay `IDLE`
- If pointer starts on a protected control → stay `IDLE` (see Section E)

**2. Pending/undecided state:**
- No visual change
- Continue receiving `pointermove` events (use `onPointerMove` on the phone frame div, or `document.addEventListener`)

**3. Movement threshold (INTENT_PX):**
- Decision is made once `Math.sqrt(dx² + dy²) > INTENT_PX`
- **Tunable constant: `INTENT_PX = 10`**
  - Calibration range: 6–14 px. Below 6 causes false horizontal captures on imprecise taps. Above 14 makes the gesture feel sluggish on slow swipes.
  - Existing code uses `8 px` as a tap-vs-drag discriminator (line 1905); `10 px` is a safe starting point that slightly favors scroll.

**4. Horizontal vs vertical direction decision:**
- `const angle = Math.atan2(Math.abs(dy), Math.abs(dx))` (0 = pure horizontal, π/2 = pure vertical)
- `const LOCK_ANGLE = Math.PI / 4` (45°) — capture horizontal if `angle < LOCK_ANGLE`
- Alternative: compare magnitudes directly — `|dx| > |dy|` (equivalent to 45°, simpler)
- The directional lock must be made in the first decisive `pointermove` only; subsequent moves track 1:1 regardless of direction

**5. Cancelling a pending category tap after horizontal capture:**
- In `PENDING`, if the `pendingTarget` is a category wedge button: store it in the ref
- On transition to `HORIZONTAL_*`: call `e.preventDefault()` on the triggering `pointermove` event
- The pending `click` event will not fire if `preventDefault()` is called on the corresponding `touchmove`/`pointermove` before release
- For React PointerEvents, `preventDefault()` on `pointermove` suppresses the synthetic click
- **Note:** This is the most fragile point. In Chromium, `preventDefault()` on `pointermove` reliably suppresses the click. Verify on Safari in a real-device acceptance test.

**6. Vertical scrolling remaining native:**
- In `SCROLL` state: do not call `setPointerCapture`; `touchAction: 'pan-y'` on the scrollable div handles native scroll
- Current scrollable div has no explicit `touchAction` — add `touchAction: 'pan-y'` to it
- Do not install a global `pointermove` listener when in SCROLL state

**7. Gesture ownership locked after capture:**
- On `HORIZONTAL_*` entry: `setPointerCapture(e.pointerId)` on the phone-frame div (or a dedicated gesture capture div overlaying the whole frame)
- Once captured, all `pointermove` events route to the drawer handler regardless of where the finger travels

**8. Reversal:**
- Already works in current implementation (G3 confirmed). The 1:1 tracking formula handles reversal naturally — `clamp(0, drawerW, startOffset + dx)` works in both directions.

**9. Release position and velocity:**
- **Position:** Existing 40%/35% threshold logic is correct. Keep.
- **Velocity:** Currently not measured. To add velocity (RECOMMENDATION — not required for initial implementation):
  ```
  velocityPx_per_ms = (e.clientX − prevX) / (e.timeStamp − prevTimeStamp)
  ```
  Record last 3–5 events. If `|velocity| > FLICK_VELOCITY_THRESHOLD` (`~0.5 px/ms`) in the gesture direction, snap to open/close regardless of position.
  - **Tunable: `FLICK_VELOCITY_THRESHOLD = 0.5 px/ms`**. Range: 0.3–1.0 px/ms.
  - Velocity is optional for MVP but makes the gesture feel significantly more responsive on fast swipes.

**10. Cancel/lost pointer:**
- `pointercancel` → treat identically to `pointerup`; snap to nearest based on current position
- Existing code already routes `onPointerCancel` to the `pointerUp` handler

**11. Left vs right drawer ownership:**
- On `PENDING` entry, record `ownerSide` based on where `startX` falls:
  - `startX < GESTURE_W` → candidate `'left'`
  - `startX > frameWidth − GESTURE_W` → candidate `'right'`
- Both sides cannot be in `HORIZONTAL_*` simultaneously. A module-level ref (`activeGestureSide: 'left'|'right'|null`) enforces this.
- On `HORIZONTAL_*` entry: set `activeGestureSide`. On `IDLE` entry: clear it.

**12. Already-open drawer closing without opening the opposite:**
- When left drawer is fully open (`drawerX = drawerW`), the left slider element is at `left: drawerW` (right edge of the open drawer). The right gesture zone starts at `frameWidth − GESTURE_W`. If `drawerW = frameWidth`, they overlap only at the very edge — low risk.
- Explicit rule: if `activeGestureSide === 'left'` and a new pointer starts in the right zone → ignore (stay `IDLE` for that pointer). The `activeGestureSide` ref prevents simultaneous open.
- Additionally: when left drawer is open, the backdrop (`onClick: onClose`) covers the right slider's position, so a tap in the right zone closes the left drawer (correct behavior).

### D3. GESTURE_W constant

- **Tunable: `GESTURE_W = SLIDER_W = 28 px`** in the initial implementation
- Calibration range: 20–44 px. Smaller = harder to grab. Larger = more false positives on content near edge.
- 28 px satisfies the "approximately ½ inch" specification (physical ½ inch ≈ 44 CSS px at 96dpi; 28 px is about ⅔ of that — a reasonable narrow zone).

### E2. Recommended exclusion method

In the gesture `pointerdown` handler:
```tsx
const isProtected = (e.target as Element).closest(
  'input, select, textarea, [contenteditable], [data-no-drawer-capture]'
);
if (isProtected) return; // stay IDLE
```

This approach:
- Works with any future controls without code changes to the gesture recognizer
- Semantic/role-based for native form controls
- Data-attribute-based for custom controls
- Does not rely on CSS selectors for geometry or class names

## F. HAPTIC CAPABILITY AUDIT

### F1. APIs available in current code/runtime

**OBSERVED FACT:** No haptic calls exist anywhere in the current TrailWeigh codebase. Zero calls to `navigator.vibrate`, `Haptics`, or any haptic API were found.

### F2. Available web APIs

| API | Status |
|---|---|
| `navigator.vibrate(pattern)` | Available in Chrome/Android, **not in Safari/iOS** |
| Web Haptics API | Proposal stage; not in any stable browser |
| `window.DeviceMotionEvent` | Motion sensing; not haptic output |
| GamePad vibration | Gamepad only |
| `navigator.share` | Already used in TrailWeigh (line 2926) — share, not haptics |

### F3. iOS/Safari behavior

**OBSERVED FACT / INFERENCE:** `navigator.vibrate` is explicitly not supported on iOS Safari. Calling it returns `false` without error. No alternative vibration API exists in the web platform for iOS.

Conclusion: **any haptic feedback on iOS is impossible via web APIs**. Do not attempt to fake it.

### F4. Android/Chromium behavior

`navigator.vibrate([10])` works in Chrome on Android. Short single pulses (5–15 ms) can serve as subtle detent feedback. Long or repeating patterns should not be used.

Patterns with meaningful semantics:
- **Capture event:** `[8]` (single very short tap)  
- **Snap to open:** `[15]` (slightly heavier)  
- **Snap to close:** `[8]` (same as capture)  
- **No continuous vibration** during drag

### F5. Respecting unsupported devices and user settings

```tsx
function hapticTap(pattern: number | number[]) {
  try {
    if (typeof navigator.vibrate === 'function') {
      navigator.vibrate(pattern);
    }
  } catch { /* silent fail */ }
}
```

- `typeof navigator.vibrate === 'function'` safely handles Safari (returns `false`) and environments where the method doesn't exist
- Wrap in `try/catch` for environments where the call throws
- No user-visible effect on unsupported devices
- Do not read `prefers-reduced-motion` to suppress haptics (they are different modalities); `prefers-reduced-motion` governs animation, not vibration

### F6. Testing strategy

Automated tests can verify that `navigator.vibrate` was **called with the right argument** by mocking it:

```ts
// In the test
const vibrateSpy = test.spyOn(navigator, 'vibrate').mockReturnValue(true);
// ... perform gesture ...
expect(vibrateSpy).toHaveBeenCalledWith([8]); // capture detent
```

This verifies the call was made without verifying physical feel. Clearly document that physical haptic feel requires a real device acceptance test.

## I. FAILURE/RISK REVIEW

### I1. Accidental drawer opening while scrolling
**HIGH RISK — CONFIRMED BUG in current implementation.** G6 showed that a purely vertical drag beginning on the slider bar opens the drawer (tap-toggle on release). After full-width category restoration (removing gutters), the gesture zone will overlap the left 28px of every category card. A user scrolling near the left edge will trigger this bug frequently. **MUST FIX with intent detection (Section D).**

### I2. Delayed-feeling category taps
**MEDIUM RISK.** With a `PENDING` state and `INTENT_PX = 10` threshold, taps must wait until the pointer moves 10px OR until pointerup. Solution: on pointerup with `totalDisplacement < TAP_PX (8)`, immediately fire the deferred tap — no delay. The delay only exists while in `PENDING` with the pointer still down.

### I3. Click firing after a drag
**MEDIUM RISK.** After a horizontal capture, the synthetic `click` event fires on pointerup unless `preventDefault()` was called on the corresponding `pointermove`. In Chromium, this works reliably; in iOS Safari, testing on device is required. Mitigation: also check `drawerX > 0` in any sensitive `onClick` handlers (return early if drawer is open and the target is the backdrop).

### I4. Pointer-capture bugs
**LOW RISK.** Current implementation uses `setPointerCapture` correctly. The new implementation should call `setPointerCapture` on the phone-frame div (not the slider element) at the point of direction decision (`HORIZONTAL_*` entry). Using `setPointerCapture` on a high-level element avoids the common bug of losing capture when the pointer leaves the original element.

### I5. Stuck dragging state
**LOW RISK.** Current `drawerDragRef.active` could get stuck if `pointerup` fires on a different element. Mitigation: route `pointercancel` to the same handler as `pointerup` (already done in the current code). Additionally, clear the drag state on `blur` and on `visibilitychange` (tab becomes hidden).

### I6. Multi-touch edge cases
**MEDIUM RISK.** Current code does not check `e.isPrimary`. A second finger on the screen while dragging could cause unexpected state. After direction lock, ignore non-primary pointers for the drawer gesture. `drawerDragRef` stores `startX`/`startOffset` without a `pointerId` — add `activePointerId` to the ref.

### I7. OS back-edge gesture conflict
**MEDIUM RISK (iOS, Android system gesture bar).** iOS devices with home indicator have a 34px safe zone at the bottom. Android's back gesture typically uses the leftmost 20dp. The GESTURE_W = 28px overlaps with the Android back gesture zone. No reliable web API prevents this conflict. Mitigation: use `overscroll-behavior: none` on the phone frame; accept that some users will trigger the OS back gesture instead of the drawer. This cannot be fully solved in a web app.

### I8. Scroll lock not released
**LOW RISK.** Native scroll is not locked — the `SCROLL` state releases capture immediately, allowing native scrolling. Risk exists only if the state machine erroneously enters `HORIZONTAL_*` on a diagonal touch. The 45° threshold (|dx| > |dy|) should prevent this for all but the most diagonal swipes.

### I9. Text-field interference
**LOW RISK.** `input`, `select`, and `textarea` elements are excluded via the `isProtected` check (Section E). Category name inputs and weight inputs are never near the edge of the screen.

### I10. z-index / pointer-events mistakes
**LOW RISK.** The existing z-index hierarchy is sound. After removing gutters, verify that `pointer-events: none` is set on the invisible gesture zone overlay when a gesture is not active, so it doesn't block taps on category cards. The current implementation uses the slider element itself (which has `touchAction: none` but receives all pointer events by virtue of being on top). In the new design, the invisible zone must pass clicks through to underlying content when not in a gesture.

### I11. Drawer causing content reflow
**WILL BE FIXED.** The current implementation causes reflow (permanent gutters). The organic design with `position: absolute` drawers and no padding on the content div eliminates reflow — categories render at full width regardless of drawer state.

### I12. Stale dimension calculations after orientation/resize
**LOW RISK.** `computeSlideW` and `computeMoreH` are recomputed in `window.resize` listener (lines 1570–1577). After orientation change, the resize event fires. If the drawer is open during resize, `drawerX` may be clamped. Mitigation: on resize, snap to `0` if the panel was closed, or re-clamp to `Math.min(drawerX, newDrawerW)`.

### I13. Reduced-motion behavior becoming instantaneous but broken
**LOW RISK.** `motionDuration()` returns `'0.01s'` — not `'0s'`. A `0.01s` transition still fires `transitionend`, so `handleDrawerTransitionEnd` runs correctly. If `'0s'` were used, `transitionend` might not fire in some browsers. The current implementation is correct.

### I14. Haptic spam
**NOT APPLICABLE.** No haptics are implemented. Future implementation should fire vibrate only on `HORIZONTAL_*` entry (capture) and on snap settle (not on every `pointermove`).

### I15. Opposing drawers opening simultaneously
**LOW RISK with `activeGestureSide` ref** (see Section D). Without the ref, both drawers could enter `HORIZONTAL_*` simultaneously with two fingers — one on each edge. The `activeGestureSide` guard prevents this. Additionally, ignore non-primary pointers for the drawer gesture.
